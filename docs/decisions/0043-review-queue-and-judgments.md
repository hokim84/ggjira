# 0043. 검토 대기 화면과 항목별 판단

## Context

M4-11(ADR 0040)로 적용된 결과마다 검토 대상(`review_targets`)이 생겼지만, 사람이 볼 곳은 이슈 하나씩 여는
`router issue reviews`와 웹 UI 이슈 화면뿐이었다. 무엇이 기다리고 있는지 한 번에 볼 목록이 없었고, 사람이 결과를
보고 내린 판단(괜찮다, 아직 아니다, 다시 해라)은 Router 어디에도 남지 않았다. ADR 0040 9항은 공유 관리자 token의
표시가 사람 승인이나 완료로 읽히지 않도록 관리 token으로 검토를 "확인"하는 쓰기 경로를 만들지 않기로 했다.
M4 백로그 후속 F01은 목적·결과·검증·위험·링크를 즉시 확인/일반 대기로 나눠 보여 주고, 책임자·부모로 거르고,
M4-11의 대상 식별을 재사용하며, 오래된 대상에 대한 판단은 서버가 거절하라고 요구한다.

## Decision

1. **검토 대기 목록**(`GET /api/v1/admin/reviews`, `ggjira router reviews`, 웹 UI `#/reviews`): 대체되지 않은
   검토 대상(취소된 실행 제외)을 최신순으로 보여 준다. 분류(`immediate`/`standard`), 상태, 책임자 accountId,
   부모 이슈로 거른다. 이슈 요약·책임자·부모는 그 실행의 승인 스냅샷에서, 결과 요약·변경·PR은 저장된 결과에서
   읽는다. Jira를 부르지 않는다.
2. **상태**는 기록에서 유도한다: `pending`(판단 없음), `held`(마지막 판단이 보류), `confirmed`, `rework_requested`,
   `merged`(검토 head와 같거나 비교할 수 없는 PR 머지), `outdated`(실행 뒤 이슈가 다시 승인됨). 기본 목록은
   `pending`과 `held`다. 상태 열이나 migration은 추가하지 않는다.
3. **판단**(`POST /api/v1/admin/reviews/:targetId/judgments`, `ggjira router reviews judge`): `confirm`(확인),
   `hold`(보류), `rework`(재작업 요청). 보류와 재작업 요청은 사유가 필요하다(2000자 이하). 기존
   `review_records`에 `action: judgment.<종류>`, `authentication: admin-token`, actor, 대상의 head(커밋 없음이면
   NULL과 `commitState`), 사유로 남는다. 감사 기록 `review.judgment.<종류>`도 남는다.
4. **판단은 기록일 뿐이다**(ADR 0040 9항을 이 범위에서 대체): 어떤 판단도 Jira 상태를 옮기거나, PR을 머지하거나,
   승인을 만들거나, 실행을 다시 시작하지 않는다. 확인은 그 이슈의 `review_required` 주의 항목만 해소한다(주의 항목은
   스케줄러가 읽지 않는다, ADR 0041). 재작업은 사람이 이슈를 다시 요청해야 시작되고, 그 결과는 새 검토 대상이 된다.
   PR 머지 → 완료 조건(ADR 0040 7항)은 판단과 무관하게 그대로다.
5. **Jira 반영**: 보류와 재작업 요청만 보고 저널(`review:<기록 id>` 배치)로 Jira 댓글 하나를 남긴다. 어느 실행의
   결과인지(attempt, 커밋), 누가(공유 관리자 token으로 적은 이름임을 밝힘), 사유, 재작업이면 다시 요청하는 방법을
   적는다. 확인은 Router에만 남긴다(M4-09의 댓글 줄이기).
6. **오래된 대상 거절**: 대상이 대체됐거나(같은 이슈의 새 결과), 이슈의 현재 승인이 대상의 승인과 다르거나,
   취소된 실행이면 409 `stale_review_target`이다. 새 결과가 있으면 `currentTargetId`를 함께 준다. 없는 대상은 404,
   잘못된 판단·사유 누락은 400이다. 거절도 `review.judgment.refused`로 감사 기록에 남는다. 화면은 거절되면 그
   이유를 위에 보이고 목록을 다시 읽는다. 유효성 판단은 서버만 한다.
7. **신원**: 판단자는 `x-ggjira-actor` 헤더의 이름이다(`admin:<이름>`). 웹 UI는 검토 화면에서 적은 이름을, CLI는
   OS 사용자 이름을 보낸다. 헤더는 ISO-8859-1만 실을 수 있어 두 클라이언트 모두 percent-encoding해 보내고 서버가
   푼다(인코딩하지 않은 이전 CLI의 값은 그대로 쓴다). 공유 token 뒤의 자기 신고 이름이므로 기록·화면·댓글에서
   검증된 신원처럼 표시하지 않는다.

## Consequences

- 사람이 "봤다"는 사실과 이유가 대상(결과·커밋)에 묶여 남는다. 새 결과가 나오면 이전 판단은 이력으로만 남고
  새 대상은 다시 `pending`이다. 과거 확인이 새 결과의 확인으로 재사용되지 않는다.
- 확인했다고 이슈가 완료로 가지 않는다. 완료는 여전히 검토 커밋과 같은 PR 머지 또는 사람의 Jira 이동이다.
- 공유 token이라 누가 판단했는지는 자기 신고다. 개인별 권한·인증이 필요한 묶음 판단은 actor 권한 모델과 함께
  F02에서 다룬다.
- 책임자 필터는 accountId로만 거른다. 표시 이름은 Router DB에 없다(Jira를 부르지 않기 위해).
- 목록은 요청마다 현재 대상 전부를 읽는다. 대상이 수천 건이 되면 페이지네이션이 필요하다.
- DB migration은 없다. 이전 Router로 되돌려도 판단 기록은 `review_records`에 남고 이전 화면·CLI에서는 이슈별
  기록으로 보인다.
