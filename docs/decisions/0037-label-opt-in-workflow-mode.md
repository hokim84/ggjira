# 0037. opt-in 라벨과 일반 상태 흐름 (label 모드)

## Context

ADR 0015 이후 AI 참여는 AI 전용 Jira 상태로 표현했다. 요청(`AI 작업 요청`)·계획 요청·결정 대기·AI 작업 완료가
따로 있고, 요청 상태로 옮기는 것이 승인이었다(ADR 0019). 그래서 팀은 기존 Jira 흐름 외에 AI용 상태와
전이 규칙을 따로 배워야 했다. 계획 요청과 구현 요청을 사람이 상태로 골라야 했고, Acceptance
Criteria·Verification이 없는 구현 요청은 보류되어(ADR 0034) 사람이 절을 직접 써야 했다.

`docs/history/M4_WORK_BACKLOG.md`는 이를 "opt-in 라벨 + 할 일/진행/검토/완료"로 바꾸자고 한다. 단, 라벨은 참여
의사이고, 승인·입력 해시·준비 검사·임대 같은 기존 안전장치는 그대로 유지해야 한다.

## Decision

1. **모드**: workspace의 `workflow.mode`가 `legacy`(생략 시 기본값) 또는 `label`이다. 상태 매핑이
   workspace 단위이므로 모드도 workspace 단위다(백로그는 프로젝트 단위를 제안했다). legacy는 지금과 똑같이
   동작한다. 모드에 따라 달라지는 판단은 `src/router/workflow-mode.ts`에 모은다.
2. **label 모드 설정**: `optInLabel`이 필수이고 공백을 넣을 수 없다. `planningStatus`·`needsDecisionStatus`는
   쓰지 않는다(있으면 설정 오류). `requestStatus`는 팀의 일반 "할 일"이다. opt-in 라벨은
   `reporting.failureLabel`·`ggjira-superseded`·v4 메타 라벨과 같을 수 없다. Router가 직접 붙이거나 떼는
   라벨이 참여를 바꾸면 안 되기 때문이다. 라벨 비교는 NFC·trim·소문자 기준이다(Jira는 라벨의 대소문자를
   보존하지만 검색에서는 구분하지 않는다).
3. **후보와 승인**: 후보는 `status = requestStatus AND labels = optInLabel`이고, 코드에서도 라벨을 다시
   확인한다. 승인 id는 requestStatus 진입과 opt-in 라벨 추가 가운데 **마지막 changelog 항목**이다. 라벨을
   떼었다 다시 붙이면 새 승인이고, 이전 job은 부활하지 않는다. 처음부터 할 일 상태에 라벨을 달고 만든 이슈는
   기존처럼 `created:<key>`다. 담당자(인간 책임자) 필수, 입력 해시 v2(ADR 0035), 준비 검사(ADR 0034)는 그대로
   추가 조건이다.
4. **job 종류**: label 모드에서는 상태가 아니라 요청이 종류를 정한다.
   - plan-task 메타가 있거나 Jira 하위 이슈(`issuetype.subtask`)이면 구현이다. 더 쪼갤 수 없으므로 계약이
     없으면 ADR 0034 준비 보류를 탄다. 에픽의 자식처럼 `parent`만 있는 이슈는 하위 이슈로 보지 않는다.
   - 하위 작업이 있는 계획(`ggjira.plan`의 `taskIds`가 비어 있지 않음)이 걸린 상위 이슈는 계획이다(재계획).
   - 그 밖의 이슈는 Acceptance Criteria·Verification이 없으면 계획, 있으면 구현이다. 계획 결과가 하나면
     PM이 상위 설명에 계약을 채우고(`renderParentPlan`) 검토로 옮긴다. 사람이 할 일로 다시 옮기면 새 승인으로
     구현이 시작된다. 검토로 옮기는 것은 배포 승인으로 해석하지 않는다.
   - 추가 라벨이나 추가 LLM 호출은 없다.
5. **철회**: 열린 job의 이슈에서 opt-in 라벨이 사라지면 기존 철회 경로(`cancelStaleJob`)를 탄다. 대기 중이면
   취소, 실행 중이면 `cancel_requested`다. Worker API의 `authorize`(commit·validate·push 직전)는 Jira를 부르지
   않고 DB만 본다. verify 루프(5초)가 철회를 반영하므로 라벨 제거 뒤 최대 5초 동안 외부 반영이 허가될 수
   있다. 이미 일어난 원격 변경을 되돌렸다고 주장하지 않는다.
6. **상태 전이**: 시작은 할 일 → 진행, 완료는 → 검토, PR 머지는 검토 → 완료다(ADR 0027). 결정 요청(계획·구현)은
   **전이하지 않는다**. 진행 상태에 남기고, 댓글로 "결정을 설명에 반영하고 할 일로 옮기라"고 안내한다. 실패는
   지금처럼 진행 상태 + 실패 라벨이다. 실패한 job은 같은 승인 아래에서 슬롯을 차지하므로 자동으로 다시 돌지
   않는다. 저널의 전이 단계는 opt-in 라벨을 함께 기록하고, 실행 직전 같은 규칙으로 승인을 다시 계산한다.
   라벨이 없는 기존 저널 행은 상태만으로 계산한다.
7. **상태 식별**: 백로그는 상태 ID 사용을 제안했지만, 이번에는 지금처럼 설정된 상태 **이름**(NFC)으로
   식별하고 `workflow-check`·`router check`로 전이 가능 여부를 확인한다. 이름은 하드코딩하지 않는다.
   ID 전환은 후속 과제다.
8. **전환(legacy → label)**: `router migrate-labels plan`은 legacy 상태별 이슈와 제안 동작을 내는 읽기 전용
   명령이다. 제안 동작은 라벨+할 일, 검토로 이동, 사람 판단, 실행 중이라 보류 네 가지다. `apply`는 사람이
   `approved`로 표시한 항목만 처리한다. 처리 직전 이슈를 다시 분류하고, 처리 뒤 재조회로 결과를 확인하며,
   이슈마다 `audit_log`에 남긴다. 전환은 workspace가 legacy일 때 한다. legacy는 라벨을 보지 않으므로 전환
   중에는 아무것도 시작되지 않는다. 모드·opt-in 라벨·요청/계획/진행 상태를 바꾸는 설정은 그 workspace에
   아직 실행될 수 있는 job(대기·임대·실행·중단 요청·복구 필요)이 있으면 409 `workspace_busy`로 거절한다.
   이전 규칙으로 승인된 job이 새 규칙에서 엉뚱하게 철회되거나 남지 않게 하기 위해서다.
9. DB migration과 Worker 프로토콜 변경은 없다. Worker는 Jira 상태를 모른다.

### 결정표

| 상황 | Jira 상태 | Router |
|---|---|---|
| 할 일, 라벨 없음 | 유지 | 후보 아님 |
| 할 일 + 라벨 + 담당자, 계약 있음 | → 진행 → 검토 | 구현 job 1개 |
| 할 일 + 라벨 + 담당자, 계약 없음(상위 이슈) | → 진행 → 검토 | 계획 job, PM이 계약을 채우거나 분해 |
| 하위 이슈·plan-task, 계약 없음 | 유지 | 준비 보류, 안내 댓글 1회 |
| 결정 필요·범위 이탈·실패 | 진행 유지 | 댓글(실패는 라벨 추가), 같은 승인으로 재실행 없음 |
| 검토 → 할 일(재작업, 계획 후 구현) | — | 새 승인으로 새 job |
| 대기·실행 중 라벨 제거 | 유지 | 취소 또는 중단 요청, 재추가는 새 승인 |
| 사람이 완료나 다른 상태로 옮김 | 존중 | 철회, 자동으로 되돌리지 않음 |
| PR 머지 | 검토 → 완료 | ADR 0027 그대로 |

## Consequences

- 기존 설정은 바뀌지 않는다(`mode` 생략 = legacy). label 모드는 workspace마다 명시적으로 켠다.
- label 모드에서는 계약 없는 요청이 보류 대신 PM으로 가므로, 사람이 Acceptance Criteria·Verification을 직접
  쓸 필요가 줄어든다. 단순 변경도 계획 → 검토 → 할 일 → 구현의 두 단계를 거친다. 계약을 직접 쓰면 바로
  구현된다.
- PM이 만든 하위 이슈에는 라벨이 붙지 않는다. 실행하려면 사람이 붙인다(배포 정책에 따른 자동 부여는 후속).
- 결정 대기가 상태로 보이지 않는다. 진행 상태의 댓글과 Router 기록(결과, 보류 목록)으로 확인한다. 즉시 확인
  항목의 정리는 후속 보고 작업(M4-09)에서 다룬다.
- 라벨 제거 후 최대 5초 동안은 commit·push 허가가 남을 수 있다.
- 상태 이름이 바뀌면 설정도 바꿔야 한다(상태 ID 사용은 후속).
- ADR 0015(상태 기반 흐름), 0019(요청 상태 진입 = 승인), 0021(결정 요청 → 결정/검토 상태)은 legacy 모드에서
  그대로 유효하다. label 모드에서는 이 ADR의 3·4·6항이 우선한다.
