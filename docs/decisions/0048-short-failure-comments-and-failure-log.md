# 0048. 실패 코드, 짧은 실패 댓글, Router 실패 로그, 댓글 언어

## Context

실패 댓글은 워커가 보고한 실패 이유와 요약 전체를 Jira에 그대로 옮겼다. 흔한 실패에서도 그 내용은 CLI의
stderr 끝부분이다. 실제 사례로 `rmcp::transport::worker … 127.0.0.1:8080/mcp`가 있다. 진짜 원인은 묻혔다. 예를
들어 계정이 쓸 수 없는 모델은 Codex 스트림의 `turn.failed`에만 있었다. 이슈를 보는 사람에게 필요한 것은
무엇이 잘못됐는지와 무엇을 해야 하는지다. 그것도 팀이 읽는 말이어야 한다. 진단용 전문은 운영자가 따로 본다.

## Decision

1. **실패 코드 표.** `src/router/failure-codes.ts`에 실패 코드(`GGJ-xxx`)마다 한국어·영어 문구를 둔다. 순수
   모듈이다. 코드 범주는 다음과 같다.
   - 1xx: 워커·실행 환경
   - 2xx: AI CLI·계정
   - 3xx: 검증
   - 4xx: 계획
   - 5xx: 연결이 끊긴 실행
   - `GGJ-999`: 분류되지 않음
2. **코드 정하기.**
   - 워커가 보고한 실패 이유는 첫 줄만 표의 규칙과 위에서부터 맞춘다(`matchFailure`). 뒤따르는 출력에 우연히
     `login`·`model` 같은 낱말이 들어 있기 때문이다. 맞는 것이 없으면 `GGJ-999`로 첫 줄을 보인다.
   - Router가 직접 아는 실패는 코드를 바로 붙인다. 시간 초과(105), 계획 적용 실패(401), 계획 없음(402), 내용
     없는 결정 요청(403), 늦게 도착한 결과(501)가 여기에 해당한다.
   - 각 코드의 뜻과 할 일은 runbook에 표로 둔다. 테스트가 표에 모든 코드가 있는지 확인한다.
3. **댓글.** 실행 실패·시간 초과·계획 적용 실패 댓글은 세 줄로 쓴다. 언어는 Router 설정
   `reporting.language`(`ko` 기본, `en`)를 따른다.
   - `실행 실패 [GGJ-xxx]: <문구>`
   - `다음: …`
   - `자세한 내용: Router 머신의 <로그 경로>`
   - 서명이 뒤따르고, 보존된 미커밋 변경이 있으면 그렇다는 한 줄을 더한다.
   - 연결이 끊긴 실행의 댓글도 같은 형태다.
4. **로그 파일.** 예전 댓글 전문을 Router 실패 로그에 영어로 쓴다. 맨 위에 코드와 댓글 첫 줄을 둔다.
   - 전문: 영향, 다음 행동, `Failure Reason`, `Summary`, `Blocking Issue`, 보존된 변경, 서명.
   - 위치: `<db 디렉터리>/failure-logs/<이슈>-<attemptId>.log`. 기본값은 `data/failure-logs/`로, 워커의
     `data/worker-logs`와 같은 위치 규칙이다.
   - 쓰는 방법: 보고 저널의 단계 `failure-log`가 댓글 단계보다 먼저 쓴다. 다시 실행돼도 같은 내용을 다시 쓸
     뿐이다. 쓸 수 없으면 단계는 skipped로 이유를 남기고, 댓글은 그대로 달린다.
5. **모든 댓글의 언어.** Router가 Jira에 쓰는 문장은 모두 `src/router/comment-text.ts`의 표에 언어별로 있고,
   `reporting.language`를 따른다. 대상 댓글은 다음과 같다.
   - 계획 시작·반영·승인·완료·승인 거부
   - 결정 요청(계획·구현)
   - 구현 완료와 검토 안내
   - 검토 보류·재작업
   - PR 머지·닫힘
   - 담당자 없음
   - 하위 작업 대체
   - 중지

   사람이나 AI가 쓴 내용(요약, 질문, 메모)은 쓴 그대로 보인다. 다른 코드가 다시 읽는 줄은 언어와 상관없이
   그대로 둔다. 결정 요청의 `planVersion:`·`decisionId:`, 답 형식 `Decision: <id>`, 서명 줄(`ggjira job:`,
   `attempt:`, `approval:`)이 여기에 해당한다. 기록에도 남는 이유는 구조화된 값으로 넘긴다. 계획 승인 거부
   이유(`PlanRefusal`)와 머지 판단(`MergeWhy`)이 그렇다. 확인 필요 항목·검토 기록에는 이전과 같은 영어
   문장을 남겨 사건 묶음이 바뀌지 않게 하고, 댓글은 설정한 언어로 쓴다. `src/pm/decision-render.ts`는 언어를
   모르고, Router가 문장을 넘긴다.
6. **Codex 원인.** Codex provider는 `turn.failed`의 오류 메시지(API 오류 본문이면 그 안의 `message`)를 실패 요약
   첫 줄에 둔다. 예: `Worker exited with code 1: <원인>`. 그래서 2xx 규칙에 맞는다.

## Consequences

- Jira 댓글만으로는 stderr를 볼 수 없다. 전문은 Router 머신의 로그 파일에서 본다. 로그 파일은 DB처럼 Router
  데이터 디렉터리(Docker에서는 볼륨)에 쌓이고, 자동으로 지우지 않는다.
- 결과 원문은 지금처럼 `results`에 남는다.
- 새 원인을 알아보게 하려면 표에 규칙과 문구를 더하고 runbook 표에 줄을 더한다.
- 실패 코드는 실행 실패 댓글에만 붙는다. 다른 댓글은 코드 없이 언어만 따른다.
- 이 변경 전에 저널에 들어간 계획 반영·하위 작업 대체 단계는 언어 정보가 없어 영어로 쓴다.
- 이슈 설명에 쓰는 계획 본문(절 제목 등)은 댓글이 아니라서 바꾸지 않았다.
- 확인 필요 항목의 원인 분류(`failed`의 cause)는 바뀌지 않는다.
- 새 DB migration과 Worker 프로토콜 변경은 없다.
