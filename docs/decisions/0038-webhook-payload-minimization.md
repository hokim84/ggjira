# 0038. Jira 웹훅 저장 최소화와 깨우지 않는 이벤트

## Context

Router는 서명이 맞는 Jira 웹훅을 delivery id로 중복 제거해 `events`에 저장하고, 미처리 이벤트가 있으면
전체 reconcile을 돌린다(ADR 0019). 판단은 늘 Jira 재조회로 하므로 웹훅 내용은 쓰지 않는다. 그런데도 payload
전체(이슈 설명, 댓글 본문, 사용자 이메일)를 저장하고 있었다. 또 댓글 이벤트와 다른 프로젝트 이벤트도 매번
reconcile을 깨웠다. Router 자신이 쓰는 보고 댓글도 그런 이벤트를 만든다. M4 백로그(M4-06)는 payload
크기·형식·대상 제한, 자기 유발 루프 방지, 저장 실패를 성공으로 숨기지 않을 것을 요구한다.

## Decision

1. 저장 형식: `{webhookEvent, issueKey, projectKey, changedFields}`만 저장한다(`summarizeJiraWebhook`).
   `projectKey`는 payload의 프로젝트 필드, 없으면 이슈 키 앞부분에서 얻는다.
2. 깨우지 않는 이벤트: `comment_*` 이벤트와 설정된 workspace에 속하지 않는 프로젝트의 이벤트는 처리됨으로
   기록한다(중복 제거와 진단용). 응답은 `202 {"status":"ignored"}`다. 프로젝트를 알 수 없으면 깨운다.
   댓글은 승인 입력이 아니다. 결정 답변 댓글은 사람이 이슈를 다시 요청할 때(그 자체가 이벤트) 반영된다.
   Router 자신의 전이·라벨 쓰기는 계속 깨운다. reconcile은 멱등이라 새로 하는 일이 없다.
3. 본문 한도를 1 MiB로 명시한다. 넘으면 413이다.
4. 저장 실패는 500으로 답한다(기존 동작, 테스트로 고정). Jira가 재전송하고, 보완 조회(60초)가 놓친 변화를
   메운다.
5. 서명 검증(SHA-256, 상수 시간 비교)과 delivery id 필수는 그대로다.

## Consequences

- 웹훅 이벤트 행으로 이슈 본문이나 사용자 정보를 복원할 수 없다. 진단에는 이벤트 종류와 바뀐 필드만 남는다.
- 댓글만 달린 변화로는 reconcile이 돌지 않는다. 보완 조회가 60초마다 돌므로 놓치는 변화는 없다.
- 이미 저장된 이전 이벤트 행은 그대로 둔다(처리 완료 후 쓰이지 않음).
