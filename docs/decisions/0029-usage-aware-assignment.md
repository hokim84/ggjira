# 0029. LLM 플랜 사용량을 워커 배정에 반영한다

## Context

워커가 LLM 플랜 사용량을 보고하게 됐다(ADR 0028). 배정은 capability·저장소 조건을 통과한 유휴 워커 중
가장 오래 배정받지 않은 워커를 골랐다. 이 순서는 사용량을 보지 않는다. 그래서 5시간 한도에 닿은 워커가
작업을 받아 한도 오류로 실패하고, 이슈에 실패 라벨이 붙는 일이 생긴다.

워커에 역할을 나눠 주는 방식도 검토했다. 모든 워커가 같은 CLI로 같은 저장소를 다루는 지금은, 역할
분리가 유휴 워커를 놀리기만 한다. capability는 환경 제약(Unity, ComfyUI 등)에만 쓰고, 분배는 "쉬는 워커
우선"을 유지하면서 사용량을 반영하기로 했다.

사용량은 연결 시와 작업 직후에만 갱신된다. 그래서 값이 오래됐을 수 있다.

## Decision

1. 워커가 job에서 쓸 provider(정책의 `providerId`)의 마지막 보고로 압력을 정한다
   (`src/router/usage-routing.ts`).
   - `exhausted`: 아직 리셋되지 않은 창 중 하나라도 100% 이상이다.
   - `high`: 아직 리셋되지 않은 창 중 하나라도 `scheduling.usage.deprioritizeAtPercent`(기본 90) 이상이다.
   - `ok`: 그 밖의 경우다. 보고가 없는 경우도 포함한다.

   리셋 시각이 지난 창은 무시한다. 리셋 시각이 없는 창은 관측 시점부터 창 길이(모르면 5시간) 동안만
   믿는다. 오래된 높은 값 때문에 워커가 영구히 제외되지 않는다.
2. `assignQueuedJobs`는 `exhausted` 워커를 후보에서 뺀다(`scheduling.usage.skipExhausted`, 기본 true).
   남은 후보는 압력이 낮은 순, 그다음 기존 공정성 순서(가장 오래 배정받지 않은 순)로 정렬한다. 후보가
   `high`뿐이면 그 워커가 받는다. 막는 것은 `exhausted`뿐이다.
3. `jobs/next`(long poll)도 온라인 워커 전체를 넘겨 같은 규칙을 쓴다. 다만 job은 요청한 워커만 받을 수
   있다. 압력이 더 낮은 유휴 매칭 워커가 있을 때만 양보하고, 그 워커가 다음 poll에서 가져간다. 공정성
   순서로는 양보하지 않는다. 지금 묻고 있는 워커에게 주는 편이 지연이 적기 때문이다.
4. 관리 API 워커 목록에 `usagePressure`를 넣는다. 웹 UI 워커 카드에 "배정 제외"와 "후순위" 배지를 보인다.

## Consequences

- 한도에 닿은 워커로 인한 실패가 줄어든다. 모든 워커가 `exhausted`면 job은 리셋까지 `queued`에 남는다.
- 보고된 값은 과거 값이다. 한도를 늘렸거나 추가 크레딧을 샀다면 워커를 재시작해야 반영된다.
- `high` 워커는 여유 있는 워커가 바쁘거나 오프라인이면 여전히 작업을 받는다.
- 이 규칙은 `RuleDecisionProvider`가 아니라 스케줄러에 있다. 라우팅 결정(무엇을 할지)과 배정(누가 할지)의
  경계를 그대로 둔다.
