# 0052. 모든 Worker의 공통 실행과 자식 승인 기록 보장

## Context

계획의 `requiredCapabilities`, Router의 허용 역량, Worker의 보고 역량이 서로 다르면
온라인 Worker가 있어도 작업이 배정되지 않았다. 기능별 실행 환경과 성공 여부는 실제
실행·검증에서 확인하므로 별도 역량 목록은 운영 부담을 더했다.

자식 계약 게시의 마지막 단계가 Jira 검색에 의존하여, 새 자식의 검색 색인 반영이 늦으면
승인 기준 기록이 없는 상태에서도 게시 완료로 처리될 수 있었다.

## Decision

- 모든 가용 Worker가 계획, 구현, 완료 평가를 수행한다. 역량 필드, 매칭 코드와 UI를 제거한다.
- 저장소 권한, 온라인 상태, 동시 실행 제한, 사용량 정책과 명시적 Worker 지정은 유지한다.
- 프로토콜은 4로 올리고 Router와 Worker를 함께 갱신한다. 기존 설정의 역량 필드는
  파싱 시 무시하며 새 설정·응답·계획에는 출력하지 않는다. 사용하지 않는 backend 목록도 제거한다.
- Migration 18은 현재 DB의 작업·Worker 역량 열을 삭제한다. 과거 마이그레이션과 감사 기록은 보존한다.
- 자식 게시 완료는 생성 결과와 유지 작업의 저널에 기록된 키로 직접 조회한다.
  부모 계획의 모든 taskId에 승인 기준 기록이 있어야 완료한다. 기존 기준은 덮어쓰지 않고,
  새 기준은 전체 계약 확인 후 한 트랜잭션으로 저장한다. 검색 누락은 완료 근거가 될 수 없다.
- 이미 누락된 기준을 복구할 때는 DB를 백업하고, 계약 게시 완료 시각과 Jira 상태 변경 이력으로
  게시 이전의 마지막 승인 진입을 복원한다. 게시 후의 사용자 승인을 기준으로 저장하여
  무효화하지 않는다. 근거가 불충분하면 자동 승인을 만들지 않는다. 복구 근거는 감사 로그에 남긴다.

## Consequences

운영자는 기능별 역량 목록을 관리할 필요가 없다. 실제 수행 실패는 기존 실행 결과와 검증 근거로
드러난다. 이전 프로토콜의 프로세스는 재시작해야 하며, 기존 입력 해시에는 제거된 계약 필드가
포함되어 있을 수 있으므로 실행 중 작업이 없는 시점에 갱신한다.

새 자식이 검색에 나타나기 전에도 승인 기준은 빠짐없이 기록된다. 계약 확인 실패 시에는
보고 단계를 대기시켜 재시도하고 게시 완료를 선언하지 않는다. 사람이 자식을 작업 중으로
옮기는 실행 승인 규칙은 그대로 적용한다.
