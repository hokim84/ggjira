# 0044. 상태 기반 AI 위임과 계획 우선 실행 (delegation 모드)

## Context

M4는 일반 할 일/진행/검토/완료 흐름에 opt-in 라벨을 얹는 label 모드를 도입했다(ADR 0037, 0039). 구현 뒤
방향을 조정했다(`docs/M4_STATUS_DELEGATION_CHANGE_REVIEW.md`). 그 결과 다음이 사용자 확정 사항이 됐다.

- 라벨이 아니라 Jira 상태 전이(보드에서 드래그)로 AI에 위임한다. 라벨은 위임·실행·취소 권한의 기준이 아니다.
- 별도 플랜 모드를 두지 않는다. 새 위임은 항상 계획부터 시작한다.
- 인간과 AI는 공용 '작업 중' 상태를 쓴다. 이 상태에 있다는 사실만으로 AI 실행이나 승인을 추론하지 않는다.
- Jira는 공용 인터페이스이고 Assignee는 인간 책임자다. PM은 계획을 반환하고, Router가 하위 티켓을 만들고
  배정하며, Worker가 실행한다.

세부 규칙 두 가지도 정했다.

- **계획 승인**은 '계획 검토 대기 → 작업 중' 전이다.
- **하위 티켓**은 지금처럼 계획 결과를 반영할 때(승인 전에) 만든다. 승인 전에는 실행만 막는다.

label 모드의 `resolveJobKind`는 계약이 있으면 바로 구현한다. 라벨을 다시 붙이면 새 승인이 된다. 계획은
일반 Review로 가서 결과 검토와 구분되지 않고, 사람이 계획을 승인하는 사건도 없다. legacy 모드로 돌아가는
것만으로는 이 의도를 만족하지 못한다. legacy에서는 계획이 선택 사항이고, 승인 단계도 다르다.

## Decision

1. **새 모드**: `workflow.mode: "delegation"`. legacy·label은 호환용으로 그대로 둔다. 모드에 따라 달라지는
   판단은 `src/router/workflow-mode.ts`, delegation 판단의 본체는 `src/router/delegation.ts`에 둔다.
2. **설정**: `planReviewStatus`(계획 검토 대기)가 필수다. `optInLabel`·`planningStatus`·`needsDecisionStatus`는
   쓰지 않는다(있으면 설정 오류). request·planReview·inProgress·review·done은 서로 다른 상태여야 한다.
   서로 다른 단계가 같은 컬럼에 숨지 않게 하기 위해서다. 상태는 지금처럼 이름(NFC)으로 식별한다.
3. **위임(계획 요청)**: `requestStatus`(AI 계획 요청)로 들어간 changelog 항목이 위임 사건이자 승인 id다.
   이 상태의 이슈는 계약 유무·하위 이슈 여부와 상관없이 **항상 planning** job 하나가 된다. 계획은 이슈가 요청
   상태에 머문 채 진행되고, 시작할 때 상태를 옮기지 않으며 시작 댓글만 남긴다. 같은 승인 id로 끝난(성공한)
   job이 있으면 다시 만들지 않는다. 실패한 job은 기존처럼 같은 승인 아래 슬롯을 차지한다. 그래서 요청 상태에
   계속 있어도 무한히 다시 돌지 않는다.
4. **계획 결과**: 계획(성공·결정 필요)은 `planReviewStatus`로 옮긴다. 결과 검토(`reviewStatus`)와 구분된다.
   계획을 반영하는 저널(하위 티켓 생성·stamp·계획 속성·재전송 보호)은 그대로 재사용한다. 결과를 저장하는
   트랜잭션에서 `plan_reviews` 행을 함께 남긴다. 이 행은 요청 승인 id, 계획 버전, outcome, task id를 담는다.
   outcome은 `planned`, `needs_decision`, `not_applied`(검증 실패) 중 하나다. 새 행이 생기면 이슈의 이전
   계획과 그 배포는 닫힌다. 하위 이슈는 위임할 수 있지만, 하위 작업을 만드는 계획은 거부한다(Jira는 하위
   작업을 중첩하지 못한다).
5. **계획 승인**: Router가 아는 열린 계획의 이슈만 Jira에서 다시 읽는다. 공용 '작업 중' 상태를 검색하지
   않는다. 승인은 최신 요청 이후의 마지막 `planReviewStatus → inProgressStatus` 이동이고, 다음을 모두 만족해야
   한다.
   - 최신 계획이 `planned`다(결정 대기·반영 실패 계획은 승인 불가).
   - 그 계획이 최신 요청에 대한 답이다.
   - 이관 기준선 hold가 없다.
   - 계획 저널이 다 반영됐고, Jira의 `ggjira.plan` 버전이 검토한 계획과 같다.

   조건을 만족하면 `plan_deployments`에 한 번(`UNIQUE (issue_key, approval_id)`) 기록한 뒤 실행을 허용한다.
   계획이 아직 반영 중이면 `waiting_plan_apply`로 기다린다. 만족하지 못하면 이동마다 한 번 이유와 다음 행동을
   댓글로 남기고 `plan_approval_refused` 주의 항목을 남긴다. 계획 없이 사람이 '작업 중'으로 옮긴 이슈는 아무
   일도 일어나지 않는다. Router는 이 전이를 만들지 않는다. Router가 만든 상태 변경은 사람의 승인이 되지 않는다.
6. **배포와 상속**:
   - tasks가 없는 계획이면 이슈 자신이 implementation job이 되고, 승인 id는 배포의 승인 id다.
   - tasks가 있으면 부모는 조정용이고 job을 만들지 않는다. 활성화할 때 Router가 계획의 하위 작업을 '작업
     중'으로 옮긴다. 이미 검토·완료에 있는 것은 옮기지 않는다.
   - 각 하위 작업은 계획 버전과 배포 승인을 상속한 implementation job이다. 승인 id는
     `<배포 승인>#<taskId>@<하위 작업의 작업 중 진입>`이다. 하위 작업에서 PM job을 다시 만들지 않는다.
   - `ggjira.plan-task`가 없는 하위 이슈(사람이 만든 것)는 가져가지 않는다.
   - 의존성 완료는 `doneStatus`이거나, F01에서 확인했거나 검토한 PR이 머지된 결과일 때만이다. Review 도달은
     완료가 아니다.
   - 모든 하위 작업이 완료되면 Router가 부모를 `reviewStatus`로 옮기고 배포를 `completed`로 둔다.
7. **철회**: 부모가 '작업 중'을 벗어나면(할 일·요청·완료 등) 배포는 `revoked`가 된다. 열린 job은 다음 확인에서
   취소되거나 중단 요청을 받는다. Worker API의 `start`·`heartbeat`·`authorize`는 Jira 없이 배포가 `active`인지
   본다. 하위 작업은 '작업 중'을 벗어나면 그 실행만 철회된다. 다시 들어오면 같은 계획 안의 새 실행이다(재시도).
   관리자의 `jobs cancel`은 그 승인을 hold한다. 부모 실행의 hold는 배포를 철회한다. 실행은 시작할 때 상태를
   옮기지 않으므로, 정상 진행 중에 허용 상태를 벗어날 일이 없다. Router의 정상 전이(계획 완료, 결과 검토,
   부모 완료)는 job이 끝난 뒤에 일어나므로 철회로 오인하지 않는다.
8. **재시도와 범위 변경**: 같은 계획을 다시 실행하려면 '계획 검토 대기 → 작업 중'으로 다시 옮긴다. 새 승인
   id로 새 배포가 생긴다. 하위 작업은 '작업 중' 밖으로 옮겼다 되돌리거나 `jobs retry`를 쓴다. 범위를 바꾸려면
   설명을 고쳐 요청 상태로 옮긴다(새 계획·새 승인). 구현 중 결정 요청과 범위 이탈은 '작업 중'에 남는다.
   댓글은 요청 상태로 옮겨 다시 계획하라고 안내한다.
9. **보고 저널**: delegation 구현의 전이 단계는 `approvalRule`을 기록한다. `plan-approval`은 부모의 계획 승인을,
   `plan-task`는 하위 작업의 작업 중 진입을 다시 계산한다. 하위 작업 이동처럼 다른 이슈를 옮기는 단계는
   `issueKey`를 함께 기록한다. 규칙이 없는 기존 저널 행은 쓰인 당시의 규칙(상태·opt-in 라벨)으로 판단한다.
   새 규칙으로 다시 해석하지 않는다.
10. **API·UI**: 이슈 조회(`GET /issues/:key/opt-in`, `issue show`)는 delegation 모드에서 단계·계획·승인·
    hold를 보여 준다. 화면은 다음에 옮길 상태를 안내한다. label 토글은 delegation 모드에서 409
    `not_label_mode`다. 위임·승인은 Jira 드래그로만 한다. Router UI가 대신 전이하면 사람의 승인과 구별할 수 없기
    때문이다. 철회·재시도는 기존 `jobs cancel`·`jobs retry`를 쓴다. 설정 화면·셋업 마법사는 모드에 delegation을
    더하고 계획 검토 상태를 받는다. `workflow-check`·`router check`는 delegation 경로의 전이를 확인한다.
    delegation 모드에서는 계획 검토·결과 검토·완료 상태도 `workspace_busy` 가드 대상이다.
11. **이관**: `router migrate-delegation plan`(읽기 전용)은 legacy·label workspace의 이슈별 의미를 보여 준다.
    - `keep`: 사람의 작업 또는 그대로 둘 결과.
    - `manual`: 이전 규칙에서 AI를 기다리던 이슈. 사람이 요청 상태로 옮겨야 위임된다.
    - `blocked`: 아직 실행될 수 있는 job이 있다.

    새 요청·계획 검토 상태는 이전 규칙이 쓰던 상태와 달라야 한다. `apply`는 실행될 수 있는 job이 없을 때만
    동작하고, Jira에 아무것도 쓰지 않는다. Jira에 이미 있는 요청 진입·계획 승인 이동을 `admin_holds`(actor
    `migration:delegation`)에 기준선으로 남길 뿐이다. 그래서 전환 자체나 전환 이전의 상태 이력은 새 요청·승인이
    되지 않는다. 이전 계획에는 `plan_reviews`가 없으므로 승인 근거가 될 수 없다. 라벨만 있는 티켓을 일괄로 요청
    상태로 옮기지 않는다. 모드 전환은 그 뒤의 설정 변경이다.
12. **저장과 프로토콜**: migration 14(`plan_reviews`, `plan_deployments`)만 추가한다. 기존 migration 1~13은 그대로
    둔다. 계획 저장과 승인 판단은 모두 Router 안에서 하므로 Worker 프로토콜 2는 바꾸지 않는다.

### 결정표

| 상황 | Jira 상태 | Router |
|---|---|---|
| 할 일(사람의 작업), 라벨 유무 무관 | 유지 | 후보 아님 |
| → AI 계획 요청 | 요청 상태 유지 → 계획 검토 대기 | planning job 1개, 시작 댓글, 계획 반영 |
| 계획 실패 | 요청 상태 + 실패 라벨 | 같은 요청으로 재실행 없음 |
| 계획 검토 대기(결정 필요 포함) | 유지 | 실행 없음 |
| 계획 검토 대기 → 작업 중, 유효한 계획 | 작업 중 | 배포 기록 → 부모 구현 또는 하위 작업 실행 |
| 같은 이동, 결정 대기·이전 요청·다른 버전 | 작업 중 | 승인 아님, 댓글 1회, 주의 항목 |
| 할 일 → 작업 중(사람) | 작업 중 | 아무것도 하지 않음 |
| 부모가 작업 중을 벗어남 | 존중 | 배포 철회, 열린 job 취소·중단 요청, 늦은 결과 미반영 |
| 하위 작업 모두 완료 | 부모 → 결과 검토 | 배포 완료 |
| 부모 구현 결과 | 작업 중 → 결과 검토 | ADR 0040~0043 검토, PR 머지는 완료로 |

### 대체 범위

- ADR 0037 §3(라벨 기반 후보·승인), §4(요청에 따른 job 종류), §6(진행·검토 전이)은 delegation 모드에서
  대체된다. label 모드에서는 그대로 유효하다.
- ADR 0039의 opt-in 토글은 delegation 모드에서 실행 제어 수단이 아니다. 라벨 API는 label 모드 전용으로 남는다.
- ADR 0040~0043(검토 대상·책임 게이트·주의 항목·실행 기록·검토 대기 화면)은 그대로 쓴다. F01 판단은 기록이고,
  계획 승인으로 재활용하지 않는다.
- M4 백로그의 F06("구 AI 상태 폐기")은 다음과 같이 다시 정의한다. 모든 workspace가 delegation으로 옮기고 label
  모드를 쓰지 않게 되는 것이 label 경로(opt-in 후보·승인·토글·`migrate-labels`)를 지울 조건이다. 지우기 전에는
  새 ADR이 필요하다.

## Consequences

- 새 위임마다 계획 호출이 한 번 더 생긴다. 계약이 이미 있는 단순 작업도 계획 → 승인을 거친다. 호출 수와 비용
  변화는 기존 실행 기록(ADR 0042)으로 관찰한다.
- 승인 판단에 Router DB의 계획 기록이 필요하다. Router 바깥(Jira만)에서 승인 여부를 재구성할 수는 없다. 다만
  Jira에는 계획 댓글, 승인 댓글, 하위 작업 이동이 남는다.
- 활성화 전에 만들어진 하위 티켓은 계획 검토 중에도 Jira에 보인다. 계획을 다시 하면 기존 supersede 규칙으로
  정리된다.
- 승인 이동은 changelog의 상태 이동 항목(from·to)으로 판단한다. Jira가 제공하는 actor는 보존할 뿐 인증 수준을
  높여 주장하지 않는다.
- 철회는 Jira 재확인 주기(활성 job 5초, 전체 조회·웹훅) 안에서 반영된다. 이미 push된 원격 변경은 되돌리지
  않는다.
- 부모 결과 검토 진입은 하위 작업의 완료(done 또는 확인된 결과)로만 판단한다. 부모 단위의 통합 검증 실행은
  후속 과제다.
