## 2. 이번 대화에서 확정된 방향

1. 라벨을 붙여 액션을 선택하는 방식 대신 Jira 상태 전환으로 AI에 위임한다.
2. 드래그로 위임하고 칸반 컬럼에서 단계와 개입 시점을 확인한다.
3. 별도 플랜 모드를 선택하지 않는다. 새로운 AI 위임은 항상 계획부터 시작한다.
4. 인간과 AI는 공용 ‘작업 중’ 상태를 사용한다.
5. Jira는 공용 업무 인터페이스, Assignee는 인간 책임자, PM은 계획 반환, Router는 하위 티켓 생성과 배정, Worker는 실행이라는 구조를 유지한다.
6. 라벨을 쓰더라도 AI 위임·실행·취소 권한의 기준으로 사용하지 않는다. 구체적인 보조 라벨 목록은 미확정이다.

기존 M4의 ‘라벨 기반 참여’와 ‘AI 전용 상태 완전 배제’ 결정을 대체한다. M4의 실행 안전장치와 기록 체계를 폐기하는 변경은 아니다.

## 3. 상태와 승인 의미 — 구현을 위한 제안

상태명은 화면 예시다. 프로젝트별 상태 ID와 허용 transition ID를 매핑한다. 컬럼과 상태의 실제 매핑을 검증하고 서로 다른 단계가 같은 컬럼에 숨지 않게 설정한다.

| 상태/전환 | 의미와 Router 동작 |
|---|---|
| 할 일 | 인간 업무 대기. AI 실행 대상 아님 |
| → AI 계획 요청 | 새로운 위임 사건. 계획 입력을 고정하고 PM job 하나 생성 |
| AI 계획 요청 유지 중 | 대기·계획 실행. 같은 요청을 polling할 때 재생성하지 않음. 실제 실행 여부는 카드/댓글에 표시 가능 |
| → 계획 검토 대기 | PM 결과·버전·분해·완료 조건·결정 사항을 기록. 아직 구현 승인 아님 |
| 계획 검토 대기 → 작업 중 | 계획 승인 전이로 사용하는 안. 현재 계획·입력·미해결 결정·권한을 검증하고 승인/배포를 영속화한 뒤 실행 허용 |
| 작업 중 | 인간과 AI 공용. 이 상태 자체만으로 AI job을 만들지 않음 |
| → 결과 검토 | 유효한 구현 결과와 검증 증거를 연결. 계획 검토와 구분 |
| → 완료 | 기존 사람 완료 및 유효 PR merge 정책 유지 |
| → 할 일 또는 명시적 취소 | AI 실행 권한 철회. 신규 배정 중단, 실행 취소 요청, 늦은 결과 반영 차단 |

‘계획 검토 대기 → 작업 중’을 승인으로 쓰는 구체적인 전이 규칙은 아직 사용자가 확정한 사항이 아니며 위 제안에 속한다. 공용 ‘작업 중’ 상태에 있다는 사실만으로 승인이나 AI 참여를 추론하는 것은 금지한다.

승인 이벤트는 특정 계획 버전·inputHash·전이 사건에 연결한다. 상태는 사람의 의사 표현, Router의 승인/배포 기록은 그 의사를 특정 실행에 연결하는 증거다. 기존 인증 수준을 과장하지 않고 사람/Router의 전이 출처와 실제 제공되는 actor 정보를 보존한다. Router가 만든 상태 변경을 새 인간 승인으로 처리하지 않는다.

다중 작업의 부모는 조정용으로 유지하고 Worker가 부모와 자식을 이중 구현하지 않게 한다. 부모 결과 검토 진입은 필요한 하위 작업과 검증 충족을 확인한다. 하위 티켓의 단순 Review 도달만으로 의존성 완료를 추론하지 않는다.

### 계획 우선의 재귀 방지

- 새로운 독립 위임은 계획부터 시작한다.
- 승인된 계획으로 생성한 말단 AI 하위 작업은 계획 버전·작업 범위·배포 승인을 상속하는 안을 제안한다. 동일 계획을 다시 분해하는 PM job을 자동 생성하지 않는다.
- 작은 작업은 기존 티켓 하나로 수행하는 계획을 허용한다. 하위 티켓을 강제로 만들지 않는다.
- 승인된 범위 안의 구현 재시도와 범위 변경을 구별한다. 범위 변경은 새 계획/승인으로, 단순 재시도는 기존 범위에 연결한 새 실행 승인으로 처리한다. 구체적 재시도 조작은 최신 UI 확인 후 확정한다.

## 5. 변경 후 반드시 확인할 시나리오

1. 라벨만 추가/제거/재추가해도 계획·구현·취소가 발생하지 않는다.
2. 라벨 없는 이슈를 AI 계획 요청으로 옮기면 PM job 하나가 생긴다. 계획 실패 후 같은 상태 유지로 무한 재시도하지 않는다.
3. 요청→철회→재요청은 다른 위임 사건이다. 중복 webhook·재시작·polling은 같은 사건의 job을 중복 생성하지 않는다.
4. 계획 성공은 계획 검토 대기로 이동하며 구현을 자동 시작하지 않는다.
5. 인간 이슈를 할 일→작업 중으로 이동해도 AI 실행이 생기지 않는다.
6. 유효한 계획 승인 전이만 현재 계획을 배포한다. 수정/폐기된 계획·미해결 결정·Router 자기 전이·이관 전이는 승인을 만들지 않는다.
7. 승인 재전송·부분 Jira 생성 실패·재시작에도 하위 티켓은 중복되지 않고 부모도 이중 구현되지 않는다.
8. 승인된 말단 AI 작업은 무한 계획/분해를 시작하지 않는다. 인간 하위 작업은 Worker가 가져가지 않는다.
9. 공용 작업 중에 있는 유효 AI 실행은 계속하되, 상태만 같은 무관한 인간 티켓은 가져가지 않는다.
10. 취소·철회·수동 완료·계획 변경 뒤 늦은 결과가 새 상태/승인/결과를 덮어쓰지 않는다. Router가 정상 진행시킨 전이는 철회로 오인하지 않는다.
11. 범위 이탈·사람 결정·실패는 Jira에 이유와 다음 행동이 보인다. 보조 라벨 제거만으로 재개되지 않는다.
12. 결과 검토·PR merge·Done의 기존 승인 최신성/검증/고위험 보호가 유지된다.
13. 기존 M4의 대기·실행·Review·Done·보류 이슈를 이관해도 자동 재실행되지 않는다. 과거 직접 구현 이력에 존재하지 않았던 계획/승인을 생성하지 않는다.

## 6. 전환과 최신 구현 확인

새 설계는 M3로의 코드 롤백이 아니다. M4의 기록/복구/보호 기능 위에서 위임 정책을 교체한다.

1. 최신 M4 저장소의 SHA·완료 보고·ADR·설정 스키마·DB migration·Worker 계약을 확인한다.
2. 라벨을 참조하는 후보 조회·배정 직전·실행 중 철회·push/PR 전 검사·관리 API·UI·설정·테스트를 추적한다. 이름만 변경하고 라벨 조건을 남기지 않는다.
3. 계획 생성·승인·배포의 현재 구현을 확인하고 위 승인 전이 제안을 확정한다. PM 계획은 신규 위임의 공통 진입으로 만들되 승인된 작업의 재귀 계획을 막는다.
4. 현재 M4 기준을 보존하고 배정을 정지한다. 활성 작업을 완료 대기하거나 명시적으로 취소한다. Jira 상태/라벨·승인·활성 attempt를 이슈별로 기록한다.
5. dry-run으로 이관 후보와 모호한 작업을 분리한다. 라벨만 있는 티켓을 일괄 AI 계획 요청으로 옮기지 않는다. 실행 중 작업은 명시적 호환 유지 또는 종료 후 전환 중 한 경로로 처리한다.
6. 새 정책의 배정은 보류한 채 후보를 대조하고 재개한다. 구 라벨 정책과 새 상태 정책이 동일 프로젝트에서 동시에 실행되지 않게 한다.
7. 이관 자체의 상태 이동으로 새 요청이 생기지 않도록 이관 식별자/사건 기준선을 영속화한다. 단순 시각 비교나 webhook actor 무시만으로 막지 않는다.
8. 문제 시 배정을 정지하고 원격 변경·이후 결과를 보존한 뒤 호환성에 맞춰 복구한다. 원본 migration이나 과거 ADR을 삭제/수정해 이력을 지우지 않는다.

최신 코드 확인 결과는 §7에 기록한다. 실제 코드 수정이나 실행 검증은 이번 분석에서 수행하지 않았다.

- `docs/m4-verification.md`에 M4-00~12 완료 근거가 있고, 그 이후 F01 구현이 HEAD와 ADR 0043에 존재한다. M4 완료 기록 말미의 ‘F01~F07 미구현’은 작성 당시 기록이며 현재 F01에는 적용되지 않는다.
- 최신 작업 폴더는 읽기만 했다. 기존 테스트 결과는 완료 기록의 진술이며 이번에 재실행한 결과가 아니다.

### 실제 동작과 의도 사이의 차이

| 실제 구현 | 새 의도와의 차이 / 수정 방향 |
|---|---|
| `workflow-mode.ts:resolveJobKind`는 label 모드에서 계약 준비가 되면 즉시 implementation을 선택 | ‘신규 위임은 무조건 계획’과 충돌. 계약 유무가 계획 생략의 근거가 되지 않게 변경 |
| plan-task 또는 Jira subtask이면 implementation | plan-task의 현재 부모 계획 버전 검사 재사용 가능. 단순 subtask라는 사실만으로 새 계획 승인까지 입증하지 않게 구분 |
| `approval.ts:computeApprovalId`는 요청 상태 진입 또는 opt-in 라벨 추가 중 최신 사건 선택 | 라벨 재부착의 새 승인 효과 제거. 계획 요청 사건과 특정 계획 승인 사건의 식별 분리 |
| `candidates.ts`는 상태와 opt-in 라벨로 JQL/후보 필터 구성 | 신규 위임 상태를 기준으로 후보 선정. 공용 작업 중 전체를 후보로 삼지 않음 |
| `issue-check.ts`는 hasOptIn으로 철회를 판단하고, job 종류별 요청 상태 또는 작업 중을 허용 | 라벨 제거 취소를 새 모드에서 제거. 상태 전이·유효 승인·입력 변경에 의한 철회는 유지. 정상 진행 전이를 철회로 오인하지 않게 변경 |
| 계획 시작도 `In Progress`, 계획 성공도 일반 `Review` 사용 | 계획 요청/실행과 인간 계획 검토를 보드에서 구분하도록 `report-journal.ts` 및 workflow 전이 검사 변경 |
| PM 결과 적용 시 `report-journal.ts`가 하위 티켓 생성·stamp·계획 속성을 저널에 기록 | ‘계획 승인 후 티켓 생성’을 택하면 기존 생성 시점 자체가 바뀜. 계획 초안 보존과 승인 후 배포 저널이 필요. 현재 생성·재전송 보호는 재사용 |
| `report-journal.ts`, `report-processor.ts` 전이 저널은 optInLabel과 approvalStatus를 보존·재검증 | 새 정책뿐 아니라 기존 미완료 저널의 구 의미도 보존. 배포 중 구 저널을 새 승인 규칙으로 재해석하지 않음 |
| `issue-opt-in.ts`, admin API, CLI, `views-issues.js`에 라벨 켜기/끄기 존재 | 위임 조작에서 제거/대체. `views-config.js`의 모드 및 상태 필드, `check.ts`, `workflow-check.ts`, setup 설정도 함께 변경 |
| F01 `review-judgment.ts`, `views-reviews.js`는 이미 구현됨 | 유지할 기능. confirm/hold/rework는 기록이며 실행 승인 아님. 계획 승인으로 재활용하지 않음. 재작업 댓글의 재요청 안내는 새 정책으로 확인/수정 |

### 단순 legacy 복귀로 해결되지 않는 이유

legacy 모드는 planningStatus와 requestStatus를 사람이 구별하는 이전 구조다. 계획이 선택 사항이고 계획 검토/승인 단계도 새 의도와 같지 않다. 따라서 `mode: legacy`로 바꾸는 것만으로는 부족하다. 기존 호환 모드를 보존하면서 새 정책을 명시적으로 도입하는 안을 권장하며, 구체적인 모드명은 구현 결정 사항이다.

### 변경 전에 확정할 두 가지 세부 규칙

1. 계획 승인 전이를 ‘계획 검토 대기 → 작업 중’으로 할지. 이 전이는 유효한 현재 계획이 있을 때만 AI 실행 권한을 만든다. 일반 인간 티켓의 작업 중 진입은 무관하다.
2. 하위 티켓 생성 시점을 계획 승인 뒤로 옮길지. 현재 코드는 계획 결과 적용 때 생성하므로 이 선택은 단순 상태명 변경보다 큰 변경이다. 승인 전 Jira에 검토용 하위 티켓을 유지하는 대안도 있으나, 어느 쪽이든 승인 전 실행은 막는다.

두 항목은 대화 중 제안에서 나온 세부 규칙이며 사용자 확정 사항으로 기록하지 않는다. 상태 기반 위임·계획 우선·공용 작업 중이라는 확정 방향은 바뀌지 않는다.

### 권장 수정 순서

1. 새 상태/승인 결정표와 ADR로 0037·0039의 대체 범위를 명시한다. 0040~0043의 책임·주의·사용량·F01 기능은 보존한다.
2. workflow 정책·후보·승인·철회와 설정 검증을 함께 변경한다.
3. 계획 초안/승인/배포 시점과 보고 저널을 연결한다. 이 부분의 추가 저장 계약은 실제 설계에 따라 결정한다.
4. API·CLI·UI·재작업 안내와 전이 점검을 같은 정책에 연결한다.
5. 현재 M4 작업과 미완료 저널을 포함한 이관 및 회귀를 검증한다. 기존 migration 11~13과 Worker 프로토콜 2를 롤백하지 않는다. 프로토콜 변경 필요성은 새 계획 저장/전달 설계가 확정된 뒤 판단한다.
