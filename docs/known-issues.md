# 알려진 문제

다음에 고칠 GGJIRA 문제를 모은다. 2026-10-29 [사용자 매뉴얼](./user-guide.md)용 시나리오를 KAN 프로젝트에서
실제로 실행하며 찾았다(KAN-53~57, gg-repo PR #8·#9, Router 설정 7 / protocol 8, Windows 로컬 Router + Worker 1대).

- 항목을 고치면 상태를 `해결`로 바꾸고 관련 ADR·커밋을 적는다. 항목은 지우지 않는다.
- 우선순위는 제안이다. P1은 실행을 막거나 사람을 오도하는 것, P2는 안내 문구·표시 오류, P3는 정리·확인 필요다.
- "원인 미확인"이라고 적은 항목은 관찰만 했다. 고치기 전에 먼저 재현한다.

## 1. 검증 명령에 자체 제한 시간이 없다

- **증상:** 병합 후 통합 검증(job `ead19235`)에서 `python3 -m unittest discover -s tests -v`가 GUI 테스트의
  실제 오류 대화상자(`messagebox.showerror`)에서 멈췄다. 10분 넘게 "검증 중"이었고 그대로 두면 작업 제한 시간
  (`execution.timeoutMs`, 이 Router는 30분)까지 단일 워커가 다른 작업을 받지 못한다. 검증 중 사용자 데스크톱에
  실제 창("Amazing Text Tool")이 떴다.
- **근거:** `faulthandler`로 재현한 스택 — `tests/test_text_stats_gui.py`의
  `test_top_five_result_scroll_resize_and_read_only`가 임시 폴더를 지운 뒤 `run_analysis()`를 다시 불러
  `text_stats_gui.py:164`의 `showerror`에서 대기했다.
- **제안:** 워커 `repositories[].validateCommand`에 제한 시간을 둔다(설정 가능, 작업 제한 시간보다 짧게).
  초과하면 프로세스 트리를 종료하고(`src/worker/`의 기존 트리 종료 사용) "검증 명령 시간 초과"로 실패 보고한다.
  동작이 바뀌므로 ADR을 남긴다. 검증 명령이 화면에 창을 띄우지 않게 할 방법(예: 헤드리스 안내)도 runbook에 적는다.
- **확인 방법:** 영원히 끝나지 않는 검증 명령을 가진 fake 저장소로 통합 검증을 돌려 제한 시간 뒤 실패·프로세스
  정리·워커 재사용을 확인한다.

## 2. 하위 작업 검증은 통과, 같은 코드의 통합 검증만 멈췄다

- **증상:** KAN-55(커밋 `6fa7242`)와 KAN-56의 하위 작업 검증은 같은 검증 명령으로 몇 초 만에 통과했다. 병합본
  (`35011b1`)의 통합 검증만 1번처럼 멈췄다. 두 커밋의 차이는 `README.md`뿐이다.
- **근거:** AI는 작업 중 Tk가 없는 Python(uv CPython 3.12, `init.tcl` 오류)을 써서 실제 Tk 테스트 3개를 건너뛰었다고
  보고했다. 워커 검증 명령의 `python3`은 Tk가 있는 Windows Store Python 3.11이다. 같은 워커 프로세스가 두 검증을
  모두 실행했는데 결과가 달랐다.
- **원인 미확인.** 하위 작업 검증이 실제로 Tk 테스트를 실행했는지(건너뛰었는지)부터 워커 로그
  (`<워커 홈>/logs/<jobId>-<attemptId>.jsonl`)로 확인한다.
- **제안:** 원인을 찾은 뒤, AI 실행 환경과 검증 명령 환경이 다르면 결과 댓글에 드러나게 할지 검토한다.

## 3. 통합 검증 실패 댓글이 읽기 어렵고 다음 행동이 없다

- **증상:** KAN-53의 "통합 검증 결과 / 검증: 미통과" 댓글이
  - 검증 명령 출력을 앞이 잘린 채(`ext_stats_gui.GuiFlowTests…`) 길게 붙였다. 실패 지점이 아닌 통과 줄이 대부분이다.
  - "다음: …" 안내가 없다. 웹 UI 작업 상세에는 "원인 해결 후 `재시도` 댓글, 범위를 바꾸려면 AI 계획"이 나온다.
  - 종료 코드를 `4294967295`로 표시한다(Windows의 -1이 부호 없는 수로 보임).
- **제안:** 출력은 끝부분 위주로 짧게 자르고 전체는 실패 기록(ADR 0048)으로 보낸다. 웹 UI와 같은 다음 행동을
  붙인다. 이미 병합된 커밋이 원인이면 `재시도`로 해결되지 않으니 "설명에 원인을 적고 AI 계획으로"를 함께 안내한다.
  종료 코드는 부호 있는 값으로 표시한다.
- **확인 방법:** 통합 검증 실패 보고 테스트에 긴 출력·음수 종료 코드를 넣어 댓글 문구를 확인한다.

## 4. 계획 반영 댓글이 없어진 AI 리뷰를 안내한다

- **증상:** "계획을 반영했습니다" 댓글 끝에 "AI 리뷰는 선택 사항입니다."가 붙는다. AI 리뷰 상태는 ADR 0055에서 없앴다.
- **근거:** `src/router/report-journal.ts:835`
- **제안:** 그 문장을 지운다. 영어 문구와 해당 테스트 기대값도 함께 확인한다.

## 5. "Router 검토 화면"이 없는 메뉴를 가리킨다

- **증상:** "사람 확인 필요" 댓글과 웹 UI 작업 상세의 다음 할 일이 "Router 검토 화면에서 확인을 기록하세요"라고
  안내한다. 검토 메뉴는 ADR 0058에서 없앴다. 실제 위치는 작업 상세 → **결과 확인·의견 남기기 → 결과 확인 기록**이다.
- **근거:** `src/router/comment-text.ts:194`, `web/router-ui/views-issues.js:187`
- **제안:** 두 문구를 실제 위치로 바꾼다. 영어 문구도 같이 본다.

## 6. 대시보드 "온라인 워커"가 실제로는 배정 가능 수다

- **증상:** 워커가 연결돼 작업을 실행하는 동안 대시보드가 "온라인 워커 0 / 2"(경고색)로 보였다. 쉬는 동안
  `router status`는 "1 online"이었다.
- **근거:** `src/router/admin-service.ts:335`의 `online: isWorkerDispatchable(...)`, 집계는 같은 파일 964행,
  표시는 `web/router-ui/views-status.js:90`.
- **제안:** "연결됨"과 "배정 가능"을 나눠 보여 주거나 라벨을 "배정 가능 워커"로 바꾼다. CLI `router status`의
  `online` 표기도 맞춘다.

## 7. 계획 본문에 AI의 내부 메모가 그대로 게시된다

- **증상:** KAN-53 계획의 Constraints에 사용자용이 아닌 문장이 실렸다.
  - "기존 Jira 하위 작업 목록과 상태는 제공되지 않았고… keepTaskKeys가 빈 배열인 것은 기존 작업 부재를 확인했다는 뜻이 아니다."
  - "Lifecycle v2에 따라…", "aggregate PR", "in-progress" 같은 내부 용어
- **제안:** PM 프롬프트(`src/pm/`)에 계획 본문은 사람이 읽는 문서이며 입력 형식·내부 필드·단계 이름을 쓰지 말라고
  적는다. 프롬프트 품질은 자동 테스트가 입증하지 않으니 runbook §24의 대표 사례로 수동 확인한다.

## 8. Done으로 옮긴 이슈의 확인 필요 항목이 남는다

- **증상:** KAN-52·KAN-47을 Done으로 옮긴 뒤에도 대시보드 "확인 필요 항목"에 "결과에 주의사항 있음"으로 남았다.
- **근거:** runbook §29의 해소 조건(검토 커밋과 같은 PR 머지, 새 결과, 새 승인)에 Done 이동이 없다. 설계대로일 수 있다.
- **제안:** Done을 사람의 최종 확인으로 보고 해소할지 결정한다. 바꾸면 ADR 0041·0061·0066과의 관계를 정리한다.

## 9. 다른 워커 소유의 spool 결과를 매번 재전송하며 403 경고

- **증상:** 워커 `cp-1`이 시작할 때마다 spool에 남은 job `4933726a`의 결과를 다시 보내다
  `403 forbidden: attempt belongs to another worker` 경고를 두 번씩 남긴다. 결과는 다른 워커(`worker-1`) 소유라
  보낼 수 없는데 지워지지도 않는다.
- **제안:** 403 `attempt belongs to another worker`처럼 다시 보내도 성공할 수 없는 응답이면 spool 항목을 격리
  (예: `spool/rejected/`)하고 한 번만 알린다. `worker results` 명령에 확인·정리 방법을 둔다.

## 10. KAN 테스트 보드에 예전 상태·AI 리뷰 열이 남아 있다

- **증상:** 보드에 지금 쓰지 않는 **AI 리뷰** 열이 있고, 상태 목록에 AI 결과 검토·AI 계획 검토·AI 작업 완료·
  작업 중·검토 중·결정 대기·AI 리뷰가 남아 있다. 매뉴얼 스크린샷에도 보여 주석으로 설명했다.
- **제안:** 남은 이슈(KAN-40·42·43 등)를 옮긴 뒤 보드 열과 워크플로우에서 뺀다. 정리 후 매뉴얼 주석과 스크린샷을
  갱신한다. 제품 문제가 아니라 테스트 프로젝트 정리 작업이다.

## 11. 대기 job이 취소되고 새 job으로 다시 생긴다

- **증상:** 하위 작업 세 개를 한꺼번에 승인하자 KAN-55·KAN-56의 대기 job(`8104d0f5`, `a469fef9`)이 시도 0회로
  취소되고, 앞 작업이 끝난 뒤 새 job(`ec5c903f`, `3d9a8a67`)으로 실행됐다. 결과는 정상이었다.
- **제안:** audit 로그로 취소 사유를 보고 의존 작업 완료에 따른 정상 경로인지 확인한다. 정상이면 웹 UI에서 취소된
  job이 오해를 주지 않게 표시하고, 아니면 원인을 고친다.

## 12. Windows에서 전체 테스트가 실패한다

- **증상:** 이 Windows 개발 머신에서 `npm run test`가 25~29개 실패했다. 파일별 재실행에서도
  `worker-codex-cli`(`spawn EFTYPE`: 테스트용 가짜 CLI 스크립트를 Windows가 실행하지 못함), `worker-claude-code-cli`,
  `worker-usage`, `fci-static`이 실패했다. 전체 실행 때만 실패한 파일(`fci`, `worker-push`, `worker-quality-review`,
  `worker-scope`)은 따로 돌리면 통과했다. Docker가 꺼져 있어 Linux 검사(`docker-compose.test.yml`)로 대신하지 못했다.
- **제안:** 가짜 CLI를 Windows에서도 실행되게(`.cmd` 래퍼 또는 `node` 스크립트) 하거나 해당 테스트를 Windows에서
  건너뛰는 이유를 명시한다. runbook §13에 이 증상을 추가한다.

## 잘 동작한 것

통합 검증 실패 뒤 부모 설명에 원인을 적고 **AI 계획**으로 옮기자, 재계획이 끝난 하위 작업 세 개를 보존하고 수정용
KAN-57만 추가했다. 첫 PR이 이미 병합됐으므로 새 부모 PR #9를 만들었고, 병합 후 통합 검증을 통과했다.
