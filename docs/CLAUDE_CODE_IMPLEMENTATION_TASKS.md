# GGJIRA: Claude Code 구현 작업지시서

## 1. 목표와 적용 범위

기존 GGJIRA MVP에 다음 흐름을 추가한다.

> 작은 작업의 범위 계약 → 승인 입력 고정 → 범위 이탈 시 중단 → 책임 게이트 → 필요한 보고만 노출 → 묶음 검토 → 부채 증거 축적

기본 구현 범위는 아래 M1~M7이다. X1~X3은 후속 확장 목록이며 이번 구현에 포함하지 않는다. 작업을 여러 단계로 나누어 수행하되, 각 단계의 완료 기준과 검증 결과를 기록한다. 설계만 작성하고 구현 완료로 보고하지 않는다.

이 문서를 전달받은 Claude Code는 대상 GGJIRA 체크아웃에서 구현한다. 이 문서를 생성한 검토 작업에서는 저장소 코드를 변경하지 않았다.

- 저장소: https://github.com/hokim84/ggjira
- 검토 커밋: `7df6a02a00f6243392f534fe28df219e49733093`
- 이전 대화의 답변 본문은 조회되지 않았다. 작업 크기, 범위 이탈, 책임 게이트, 기술 부채·변경 저항, 사람의 주의 필터, Jira 보고·묶음 검토라는 주제를 기준으로 작성했다.
- 아래 필드명과 정책은 구현 제안이다. 이전 대화에서 확정된 스키마나 수치 기준으로 취급하지 않는다.
- 시작 시 현재 브랜치의 `AGENTS.md`, `CLAUDE.md`, 최신 코드와 ADR을 확인한다. 기준 커밋 이후 이미 구현된 내용은 재구현하지 말고 차이를 기록한다.

## 2. 유지할 아키텍처와 기존 기능

- Jira가 인간과 Agent의 공용 업무 인터페이스이며 승인·책임 기록의 기준이다.
- Router 한 대와 SQLite, 여러 Worker 구성을 유지한다.
- Jira API는 Router만 호출한다. Worker는 Jira나 Router DB에 직접 접근하지 않는다.
- Jira Assignee는 인간 책임자다. PM은 계획만 반환하며 Router가 하위 티켓을 생성한다.
- 기존 승인 식별자, 계획 버전, lease, 취소, spool, 결과 중복 방지, 보고 저널·복구 기능을 재사용한다.
- 기존 PM 분해, dependency 검사, capability 배정, 웹 셋업·설정·워커 관리, push·PR 생성·merge 감지를 재구현하지 않는다.
- 기존 보고 저널의 batch는 Jira 반영·재시도 단위다. 사람의 묶음 검토와 혼동하지 않는다.
- Jev `readiness`·`modelTier`는 계속 관찰 모드다. MVP에서 자동 배정 차단이나 모델 선택에 사용하지 않는다.
- 정상 완료는 검토 상태로 이동한다. 기존 PR merge 후 Done 전이는 유지하되 새 책임 게이트와의 일관성을 검증한다.
- 빌드 없는 `web/router-ui/` 구조를 유지한다. 별도 프론트엔드 프레임워크·서비스·메시지 브로커를 도입하지 않는다.

## 3. 구현 순서

`M1 + M2 → M3 → M4 + M5 → M6 → M7`

M1에서 계약을 정하고, M2에서 그 계약이 실행 도중 바뀌지 않도록 한다. M3에서 구현 Agent의 결정 요청을 정상 처리한 다음 M4~M6으로 사람의 판단과 보고를 연결한다. M7은 앞선 결과 기록을 재사용한다.

## M1. [P0] 작은 작업의 범위 계약과 준비 검사

### 현재와의 차이

현재 계획에는 acceptance·dependencies·constraints가 있고 PM 프롬프트도 독립 완료 단위를 요구한다. 하지만 개별 작업의 범위 계약과 준비 조건을 강제하지 않는다. `maxTasksPerPlan`은 티켓 수 제한이며 작업 크기 제한이 아니다.

### 구현

1. 기존 acceptance를 재사용하고 작업별 범위 계약에 다음 의미를 추가한다. 실제 필드명은 기존 스타일에 맞춘다.
   - `inScope`: 제공할 동작·결과
   - `outOfScope`: 이번 작업에서 제외할 결과·설계 변경
   - `affectedAreas`: 예상 영향 영역. 단순 참고 영역과 강제 허용 경로는 구별한다.
   - `verification`: acceptance를 확인할 명령·관찰 방법
2. PM 스키마, provider용 JSON Schema, Jira 렌더링·파싱, envelope와 승인 스냅샷을 일관되게 연결한다.
3. 기본 원칙은 독립적으로 검증 가능한 결과 하나다. 단순한 구현 절차를 Jira 하위 티켓으로 쪼개지 않는다.
4. acceptance와 검증 방법이 없는 구현 요청은 Router에서 보류하고 보완 내용을 안내한다. 계획 요청까지 같은 조건으로 막지 않는다.
5. 여러 독립 결과가 섞인 작업은 PM이 분해하거나 결정 요청으로 반환한다. 자연어 의미를 규칙 검사만으로 완벽히 판정한다고 가정하지 않는다.
6. 사람이 직접 만든 Jira 티켓과 PM 생성 티켓에 동일한 준비 조건을 적용한다. 기존 티켓의 보완 절차를 runbook에 적는다.

### 연결 지점

`src/pm/plan.ts`, `src/pm/prompt.ts`, `src/pm/plan-render.ts`, `src/issue/requirements.ts`, `src/router/decision.ts`, `src/contracts/envelope.ts`

### 완료 기준

- acceptance 또는 검증 방법이 없으면 구현 Worker가 시작하지 않는다.
- 보류 사유는 재조회마다 새 댓글로 반복되지 않는다.
- 계획 요청은 요구사항이 불완전해도 분석·보완할 수 있다.
- 단순 문구 변경은 독립 결과 하나로 처리하고 불필요한 하위 티켓을 만들지 않는다.
- 계획 스키마와 provider JSON Schema의 일치, 렌더링·파싱 왕복을 검증한다.

## M2. [P0] 승인 입력 해시 누락 보완

### 현재와의 차이

현재 `computeInputHash`는 파싱된 objective·acceptance·dependencies·constraints·capabilities·계획 버전을 사용한다. 전체 설명과 실행 전략은 직접 포함하지 않는다. Worker는 제목과 설명을 실행 지시로 받으므로 해시가 실행 지시 전체를 대표하지 않을 수 있다.

### 구현

1. 승인 입력의 canonical representation을 정의한다. Worker가 받는 제목·실행 설명·실행 전략·M1 계약과 기존 배정 조건을 빠짐없이 포함한다.
2. Router가 만드는 보고용 정보와 실행 지시를 구별한다. 실행 의미가 같은 입력의 정규화 규칙을 명시한다.
3. snapshot, inputHash, 실행 envelope가 같은 승인 내용을 가리키도록 한다.
4. 변경된 입력은 기존 취소·보류 경로로 처리하고 새 승인 전까지 재배정하지 않는다.
5. 해시 계산 방식 변경 시 기존 저장된 job을 어떻게 처리할지 정한다. 운영 중 job을 새 해시로 조용히 덮어쓰지 않는다.

### 연결 지점

`src/router/approval.ts`, `src/router/issue-check.ts`, `src/router/scheduler.ts`, `src/router/envelope.ts`, `src/contracts/envelope.ts`

### 완료 기준

- 일반 설명, 제목, 실행 전략, 범위 계약 변경이 실행 권한 철회로 이어진다.
- Router의 보고 댓글 추가는 철회를 유발하지 않는다.
- 변경된 작업은 같은 승인으로 자동 재실행되지 않는다.
- commit·validate·push 직전 권한 검사와 재시작 후 승인 검사에서도 동일하게 동작한다.

## M3. [P0] 구현 중 범위 이탈과 결정 요청 반환

### 현재와의 차이

현재 구현 실행기는 provider 결과를 주로 summary로 처리한다. 결과 계약에는 `needs_decision`이 있지만 보고 경로는 계획의 `plan.decision`을 요구한다. 구현 Agent가 설계 결정을 사람에게 넘기는 경로를 완성해야 한다.

### 구현

1. 기존 planning decision과 공통 의미를 갖는 구현 결과 스키마를 정의한다. 계획 객체를 가짜로 만들어 끼워 넣지 않는다.
2. 구현 provider에 구조화된 출력을 요청한다. 최소한 outcome, summary, scope deviation, decision request, verification evidence를 다룬다.
3. 구현 프롬프트에 범위 확대가 필요한 경우 중단하고 이유·선택지·영향·권고를 반환하도록 명시한다.
4. Git 변경 경로를 계약과 대조한다. 새 파일·삭제·rename을 포함하고, 경로 이탈과 의미상 범위 이탈을 구별한다. 경로 검사만으로 의미상 이탈이 없다고 단정하지 않는다.
5. 이탈 또는 결정 필요 결과는 일반 성공과 구별하여 보존하고 기존 `needsDecisionStatus`로 보고한다. 상태 미설정 시 기존 fallback을 따른다.
6. 범위 이탈 결과를 일반 commit·자동 push·PR 생성 경로로 흘리지 않는다. 로컬 변경 증거는 보존하고 위치·정리 방법을 기록한다.
7. 사람의 범위 수정·재승인 후 새 attempt로 재개한다. 이전 승인을 재사용하지 않는다.
8. 부정확한 JSON, 필수 증거 누락, provider 오류를 성공으로 간주하지 않는다. Claude Code와 Codex 경로 모두 처리한다.

### 연결 지점

`src/worker/prompt.ts`, `src/worker/provider.ts`, `src/worker-runtime/executor.ts`, `src/worker-runtime/runner.ts`, `src/contracts/envelope.ts`, `src/router/worker-service.ts`, `src/router/report-journal.ts`

### 완료 기준

- 승인 밖 API·데이터 모델 변경이 필요하면 결정 대기로 반환하고 자동 push하지 않는다.
- 일반 실패, 계획 결정 요청, 구현 결정 요청을 구별한다.
- spool 재전송·Router 재시작에도 결과와 결정 요청이 중복 생성되지 않는다.
- 재승인 전 실행이 시작되지 않으며 stale attempt의 늦은 결과가 새 작업을 완료 처리하지 않는다.

## M4. [P1] 책임 게이트와 검토 대상 고정

### 구현

1. 작업에 승인 계약 버전과 Git base/head commit을 연결한다. acceptance별 검증 결과는 pass·fail·미검증을 구별한다.
2. 마이그레이션·공개 계약·권한 정책 등 고위험 영역을 프로젝트 설정으로 지정할 수 있게 한다. 실제 변경과 대조하고 판정 근거를 남긴다.
3. 기존 `authorize`는 실행 권한 확인으로 유지한다. 사람의 검토 기록과 같은 의미로 취급하지 않는다.
4. 고위험, 범위 이탈, 검증 실패·누락은 일반 묶음 검토 대상에서 제외한다.
5. 검토 기록은 정확한 issue·attempt·approval/inputHash·head commit에 묶는다. commit 또는 계약이 바뀌면 이전 검토가 유효하지 않음을 표시한다.
6. 기존 관리자 공유 token만으로 실제 Jira Assignee 신원을 인증했다고 주장하지 않는다. MVP에서 웹은 검토 의사 기록과 Jira 이동을 돕고, Jira 승인과 GitHub merge를 대체하지 않는다.
7. 고위험 PR의 필수 사람 리뷰는 GitHub 보호 규칙이 담당한다. 앱 내부 표시만으로 merge를 차단했다고 보고하지 않는다. MVP에서는 필요한 설정과 수동 검증 절차를 문서화한다.

### 연결 지점

`src/worker-runtime/executor.ts`, `src/router/worker-service.ts`, `src/contracts/envelope.ts`, `src/router/db/`, `src/router/github.ts`

### 완료 기준

- 검토한 commit 이후 변경이 생기면 기존 검토는 최신 결과의 승인으로 표시되지 않는다.
- Agent의 성공 결과나 웹의 검토 표시만으로 Done 전이가 발생하지 않는다.
- 정상 PR merge 후 기존 Done 처리와 상태·승인 보호가 유지된다.
- Git 없이 직접 편집하는 작업은 commit 기반 검증이 불가능함을 표시하고 자동 묶음 대상으로 넣지 않는다.

## M5. [P1] Jira 보고 정책과 사람 주의 필터

### 구현

1. 보고 저널 생성 전에 순수 함수 형태의 분류 정책을 둔다. 최소 분류는 `즉시 확인`, `묶음 검토`, `내부 기록`이다.
2. Jira 상태와 결과 보고를 누락하지 않으면서 사람에게 노출하는 정보량을 줄인다. 기존 journal의 중복 방지·재시도·불확실한 쓰기 처리를 유지한다.
3. 댓글은 변화 → 영향 → 필요한 사람 행동 → 근거 링크 순으로 요약하고, 상세 로그를 본문에 복제하지 않는다.
4. dedup key는 최소한 작업·승인·원인·사건 종류를 반영한다. 같은 장애의 반복과 새로운 장애를 구별한다.
5. 분류 근거, 최초·최근 발생, 반복 횟수, 해소 여부를 보존한다. 정상화·새 증거·심각도 변화는 새 변화로 다룬다.

### 기본 정책

| 사건 | 기본 노출 | Jira 처리 |
|---|---|---|
| heartbeat·polling·정상 lease 갱신 | 내부 기록 | 댓글 없음 |
| 정상 실행 시작 | 상태로 확인 | 기존 진행 상태 전이 유지 |
| 정상 완료·검증 통과 | 묶음 검토 | 간결한 결과·증거·PR 댓글과 검토 상태 |
| 범위 이탈·사람 결정 필요 | 즉시 확인 | 결정 요청 댓글과 결정 대기 상태 |
| 최종 실패·복구 필요·필수 검증 누락 | 즉시 확인 | 원인·영향·다음 행동 요약. 기존 복구 의미 유지 |
| 내부 일시 오류의 자동 재시도 | 내부 기록 | 해결될 때까지 동일 댓글 반복 금지 |
| PR merge·close | 기존 정책 유지 | 중복 없는 결과 댓글·허용된 상태 전이 |

외부 알림 채널은 새로 추가하지 않는다. MVP의 즉시 확인은 Jira 및 검토 화면에 즉시 노출되는 것을 뜻한다.

### 연결 지점

`src/router/report-journal.ts`, `src/router/report-processor.ts`, `src/router/db/events.ts`, `src/router/db/audit.ts`, `src/router/daemon.ts`

### 완료 기준

- polling을 반복해도 Jira 댓글·미해결 주의 항목 수가 증가하지 않는다.
- 정상 이벤트가 많아져도 결정·복구 필요 항목이 가려지지 않는다.
- 필터링된 상세 기록은 관리 API로 조회할 수 있다.
- 재시작·재전송·Jira 쓰기 실패 시 기존 보고 신뢰성이 유지된다.

## M6. [P1] 기존 웹 UI에 검토 대기와 묶음 검토 추가

### 구현

1. 기존 hash router에 검토 화면을 추가한다. 새 프레임워크를 도입하지 않는다.
2. 즉시 확인 항목과 일반 검토 대기를 구분하고 책임자·부모 티켓·위험도로 필터·그룹화한다.
3. 기본 카드에는 목적, 변경 요약, acceptance 검증 상태, 위험·결정 요청, Jira·PR 링크만 표시한다. 상세 기록은 펼쳐서 본다.
4. MVP 묶음 검토는 여러 항목을 한 화면에서 보고 항목별 판단을 남기는 기능이다. 여러 Jira 이슈를 한 번에 승인하거나 PR을 일괄 merge하지 않는다.
5. 판단 상태는 확인·보류·재작업 요청 등 최소 의미로 정의한다. 실행 승인과 구별하고 Jira에 필요한 판단 기록을 Router journal로 남긴다.
6. 기존 admin API와 인증 방식을 재사용한다. 검토 actor의 인증 수준을 정확히 기록한다.
7. 리뷰 대상이 오래되었으면 서버가 거절하고 최신 정보를 다시 보여준다. UI만으로 유효성을 판단하지 않는다.

### 연결 지점

`web/router-ui/app.js`, `web/router-ui/dom.js`, `web/router-ui/style.css`, 새 review view, `src/router/admin-service.ts`, `src/router/server.ts`, `src/router/db/`

### 완료 기준

- 한 항목을 보류해도 다른 항목의 검토를 기록할 수 있다.
- 고위험·검증 누락 항목은 일반 묶음에서 제외된다.
- 기록마다 issue·attempt·검토 대상 commit 또는 명시적 commit 없음·actor·시각이 남는다.
- 검토 후 재작업 결과가 나오면 새 검토 대상으로 나타난다.
- 기존 셋업·워커·설정·점검 화면이 정상 동작한다.

## M7. [P1] 기술 부채와 변경 저항의 최소 증거 수집

### 구현

1. 부채 후보는 코드 위치, 관찰 사실, 증거 링크, 이번 작업 영향, 후속 조치, 책임자를 갖는다. Agent 제안과 사람 채택을 구별한다.
2. 변경 저항은 duration 하나로 점수화하지 않는다. 재시도, 검증 실패, 범위 확대, 재작업과 그 원인을 기존 attempt·result에서 연결한다.
3. 원인은 최소 코드 구조·요구사항 변경·환경/도구 장애·미확인으로 구별한다. Agent 추정은 사실로 확정하지 않는다.
4. 같은 부채 후보의 중복을 합치고 검토 화면에서 채택·보류·기각할 수 있게 한다.
5. 사람이 채택한 후보만 후속 Jira 작업으로 연결한다. 생성은 Router를 거치며 기존 생성 중복 방지·불확실성 처리를 적용한다. 이 경로가 과도하면 MVP는 사람이 만든 티켓 키 연결까지로 제한하고 그 한계를 명시한다.

### 연결 지점

`src/contracts/envelope.ts`, `src/worker-runtime/executor.ts`, `src/router/db/attempts.ts`, `src/router/db/results.ts`, 새 후보 저장·관리 API, 검토 화면

### 완료 기준

- 근거 없는 평가 문장만으로 확정 부채를 만들지 않는다.
- 환경 실패나 요구사항 변경을 자동으로 코드 부채로 집계하지 않는다.
- 모든 후보가 자동 Jira 티켓으로 생성되지 않는다.
- 채택한 후보에서 원래 작업·증거·후속 Jira 티켓을 추적할 수 있다.

## 4. 계약·마이그레이션·운영 요구사항

- Wire 필드나 결과 의미가 호환되지 않게 바뀌면 `PROTOCOL_VERSION`과 관련 schema·client·server·fixture를 함께 갱신한다. 버전이 다른 Worker는 실행 전에 명확히 거절한다.
- SQLite migration은 append-only다. 기존 배포 migration을 수정하지 않는다. 구 DB에서 새 DB로의 전환과 재실행을 테스트한다.
- 기존 결과·작업에서 새 필드가 없는 경우의 읽기·표시 정책을 정의한다. 증거 없음과 정상 확인을 혼동하지 않는다.
- 취소·재승인·재시도는 기존 상태 머신을 확장하거나 재사용한다. 중복 실행을 유발하는 별도 루프를 만들지 않는다.
- 새 준비 보류·결정 대기가 영구 대기나 자동 재실행 반복을 만들지 않게 한다.
- Jira·Worker 장애가 사람의 승인·검토로 오인되지 않아야 한다.
- ADR 번호는 최신 목록을 확인한 뒤 정한다. 계약·중단 정책·검토 의미와 기존 결정의 차이를 기록한다.
- `docs/architecture.md`, 관련 ADR, `docs/runbook.md`, 필요한 예시 설정을 함께 갱신한다.

## 5. 필수 검증 시나리오

1. 정상 소규모 변경: 준비 검사 → 실행 → 검증 → 간결한 Jira 결과 → 검토 대기 → 기존 PR merge 후 Done.
2. acceptance·검증 방법 없는 구현 요청: 시작 차단·보완 안내·반복 댓글 없음.
3. 실행 중 제목·일반 설명·전략·계약 변경: 취소·권한 철회·재승인 전 재실행 없음.
4. 구현 중 범위 이탈: 결정 대기·증거 보존·자동 push 없음·재승인 후 새 attempt.
5. 고위험 변경: 개별 검토·정확한 commit 연결·이전 검토 재사용 방지.
6. 검증 실패 또는 미검증: 정상 묶음 검토 대상 제외.
7. 결과 재전송·Jira 반영 재시도·Router 재시작: 댓글·검토 항목·후속 티켓 중복 없음.
8. 작업 재승인 뒤 이전 결과 도착: 최신 승인·검토·상태를 덮어쓰지 않음.
9. 같은 장애 반복: 내부 이력은 보존하고 사람에게 같은 항목을 반복 생성하지 않음.
10. 부분 검토·보류·재작업 결과: 항목별 기록과 새 버전 검토가 독립적으로 동작.
11. 부채 후보: 환경 장애와 구별·중복 병합·사람 채택 전 자동 티켓 생성 없음.
12. 기존 DB·결과·Worker 호환성: 마이그레이션과 명시적 버전 불일치 처리 확인.

자동 테스트에는 Fake Jira/Worker, fetch mock, loopback HTTP를 사용한다. 외부 Jira·GitHub·실제 AI CLI 호출을 넣지 않는다. 프롬프트 테스트는 필수 문구 존재만으로 의미상 작업 분해 품질을 입증했다고 보고하지 않는다. 대표 사례 수동 검토 절차도 기록한다.

최종적으로 저장소의 `npm run check`와 `npm run build`를 수행한다. Windows 전체 테스트가 멈추면 기존 runbook에 따라 파일별 검증을 수행하고 전체 검사 미완료 사실을 명시한다. 실제 연동 확인은 설정된 테스트 환경이 있을 때만 수행하고 수행 여부를 기록한다.

## 7. 토큰 소비와 LLM 호출 최소화 원칙

### 구현 원칙

- 승인 해시, 필수 필드 준비 검사, 변경 경로 검사, 보고 분류·중복 제거, 묶음 검토 집계는 일반 코드와 DB 조회로 구현한다. 이를 위한 별도 LLM 호출을 추가하지 않는다.
- 범위 계약은 기존 PM 호출에서 함께 작성하고, 검증 결과·결정 요청·부채 후보는 기존 Worker 최종 구조화 응답에서 함께 반환한다. 보고용 재요약 Agent나 매 작업의 별도 부채 분석 호출을 추가하지 않는다.
- 의미상 범위 이탈은 기존 구현 Agent가 계약과 비교해 보고한다. 일반 코드 검사가 의미상 이탈을 완전히 판정한다고 가정하지 않는다.
- 부채 후보가 없으면 빈 목록을 반환한다. 모든 작업에서 서술형 부채 보고서를 생성하지 않는다.
- 전체 로그·과거 댓글·이전 결과를 다음 프롬프트에 반복 삽입하지 않는다. 현재 승인 계약, 관련 결정, 필요한 근거만 전달하고 상세 기록은 링크·식별자로 연결한다. 필요한 실행 맥락과 승인 근거를 임의로 생략하지 않는다.
- Jira 보고 재시도, 결과 spool 재전송, 검토 화면 갱신은 저장된 결과를 재사용한다. 이런 동작이 PM·Worker·요약 모델을 다시 호출하지 않도록 한다.
- 기존 Jev 관찰 호출은 유지하되 새 자동 판단 호출로 확대하지 않는다. 호출 수와 사용량은 PM·구현 호출과 구분해 측정한다.

### 예산 가정과 측정

- 초기 계획값은 동일한 작업 구성에서 총 토큰 소비 약 10~30% 증가, 예산 기준 +20%, 검토 기준 +30%로 둔다. 이는 실측이나 성능 보장이 아니며, 자동 실행 중단 한도도 아니다. 실제 결과에 따라 조정한다.
- 비교의 주 지표는 실행 1회당 토큰이 아니라 **완료된 작업당 토큰**이다. 분해 후 하위 티켓 수가 늘어도 같은 원래 요구사항 단위로 집계하여 개선 효과를 부풀리지 않는다.
- 순증가량은 `계약·보고 추가 토큰 + 추가 계획·재개 토큰 - 감소한 실패·재작업 토큰`으로 해석한다. 재작업 감소 효과는 측정 전까지 확정하지 않는다.
- provider가 제공하는 범위에서 입력·출력·캐시 관련 토큰, 모델, 호출 종류, job·attempt, 재시도·재작업, 완료 여부를 기록한다. 공급자가 보고하는 추론 토큰 등 세부 항목의 포함 관계를 확인하여 이중 합산하지 않는다.
- 제공되지 않는 사용량은 0으로 저장하지 말고 미확인으로 표시한다. 누락률도 함께 보고한다. 새 사용량 조회를 위해 별도 추론 호출을 하지 않는다.
- 부모 계획 호출과 모든 하위 작업·실패·재개 호출을 원래 요구사항에 귀속한다. 미완료 작업 소비는 별도로 표시하고 성공 작업 집계에서 숨기지 않는다.
- 변경 전후의 유사한 작업 크기·종류·모델을 비교하고, 작업 수·기간·완료율·재작업률을 함께 제시한다. 모델이나 작업 구성 변화에 의한 차이를 기능 추가 비용으로 단정하지 않는다.
- 토큰 증가율과 실제 요금 증가율은 구별한다. 요금 환산은 모델·입출력·캐시 적용과 확인된 가격을 기준으로 별도 수행한다.

### 연결 지점과 완료 기준

- 기존 provider 결과·usage 수집, `src/worker-runtime/runner.ts`, `src/contracts/envelope.ts`, Router 결과·attempt 저장을 확인하고 실제 토큰 사용량 기록이 부족한 부분만 보완한다. 기존 한도 사용률을 토큰 수로 오인하지 않는다.
- Fake provider로 정상 호출·실패·재개·사용량 미제공 사례를 검증한다. 결과 재전송과 보고 재시도는 토큰·호출 수를 중복 집계하지 않아야 한다.
- M1~M7이 보고·검토만을 위한 추가 LLM 호출을 만들지 않는지 검증한다. 원래 요구사항 기준으로 계획·하위 작업·재작업 비용을 합산할 수 있어야 한다.
- 초기 비교에서 +30%를 넘으면 호출 횟수·프롬프트 크기·출력 크기·재작업을 분리해 원인과 개선안을 보고한다. 토큰 절감을 위해 필수 검증이나 책임 게이트를 생략하지 않는다.
