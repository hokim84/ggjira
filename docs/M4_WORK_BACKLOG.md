# GGJIRA M4 작업 백로그 — Jira AI opt-in과 간소화된 작업 흐름

작성일: 2026-10-18 · 상태: M4-00~12 구현됨(검증 기록: `docs/m4-verification.md`) · 우선순위: P0 필수 안전장치, P1 M4 사용자 기능, P2 후속 개선

## 1. 기준과 문서의 한계

- 사용자 진술을 기준으로 M3까지 구현된 상태다. **M3를 검증·push·tag하여 기준선을 확보한 뒤 M4를 시작한다.** 이 문서 작성 중 push/tag 또는 구현 변경은 수행하지 않았다.
- 참조 대화: 「기술 부채 수치화 방법」(6acc430a-a168-83ee-8a7f-28212f30f8ee). 조회 가능한 사용자 메시지는 AI 전용 상태의 간소화, 라벨 opt-in, Router 웹 UI의 Jira 라벨 관리, M3 이후 기준선 확보를 다룬다. assistant 답변 본문은 참조 표식으로만 반환되어 세부 합의를 복원할 수 없었다.
- 로컬 `CLAUDE_CODE_IMPLEMENTATION_TASKS.md`의 작은 범위 계약, 승인 입력 고정, 범위 이탈 중단, 책임 게이트, 간결한 보고 원칙을 참고했다. 이 문서에 적힌 구현 현황이나 코드 경로를 현재 사실로 검증하지 않았다.
- **(작성 당시) 실제 저장소 구현은 검사하지 않았다.** 아래 티켓의 첫 작업은 해당 기능의 존재·차이를 확인하는 것이다. 이미 구현된 기능은 재구현하지 않고 회귀 검증한다.
- 라벨명, 설정 모드, 예외 표시, 티켓 ID는 이번 백로그의 제안이다. Jira에 생성된 실제 티켓이나 확정된 스키마가 아니다.
- 기존 작업지시서의 M4는 ‘책임 게이트와 검토 대상 고정’이었다. **이번 M4는 ‘라벨 기반 AI 참여와 상태 간소화’로 재편한다.** 책임 게이트의 최소 안전장치는 포함하고, 완전한 검토 UI와 묶음 검토는 후속으로 옮긴다.

### 기존 M3 이후 작업의 승계

기존 M4~M7은 아래와 같이 승계한다. 번호가 달라져도 인수 조건을 폐기하거나 구현 완료로 간주하지 않는다.

| 기존 작업 | 이번 M4에서 유지할 범위 | 후속 범위 |

| M5 보고 정책·사람 주의 필터 | M4-09의 간결한 보고, 즉시 확인/일반 검토 대기/내부 기록, 중복·해소·재발 관리 | F07의 digest |
| M6 검토 대기·묶음 검토 | Jira 댓글과 기존 UI에서 보류 이유·다음 행동 확인 | F01 기본 검토 대기 화면 → F02 묶음 검토 |
| M7 부채·변경 저항 증거 | 기존 결과·attempt·실패/재작업 원인·사용량을 보존. 새 부채 판정은 요구하지 않음 | F03 후보 기록 → F04 후속 티켓 연결, F05 비교·분석 |
| 공통 호환성·검증·LLM 호출 최소화 | M4-07·10·12와 전 티켓 공통 원칙 | 상세 분석·비용 최적화 |

기존 `needsDecisionStatus`에 의존하는 처리는 label 모드에서 보류 사유와 사람 행동 안내로 바꾼다. legacy 모드의 기존 의미는 전환 전까지 유지한다. 기존 보고 분류의 ‘묶음 검토’는 이번에는 ‘일반 검토 대기’로 부르며, 묶음 승인 기능이 존재한다는 인상을 주지 않는다.

## 2. 유지할 구조와 달라지는 점

Jira는 인간과 Agent의 공용 작업 인터페이스로 유지한다. Router가 Jira API 호출·배정·결과 반영을 담당하고, PM Agent의 분석 결과를 받아 하위 티켓을 생성한다. Worker는 작업을 실행하고 결과를 Router에 반환한다. Jira Assignee는 인간 책임자이며 Agent 배정과 구별한다. Router·SQLite·Worker 구성을 유지하고 새 서비스나 프레임워크를 도입하지 않는다.

| 항목 | 기존 전제 | M4 목표 |
|---|---|---|
| AI 참여 의사 | AI 전용 상태 사용 | 설정된 opt-in 라벨로 표현 |
| 업무 진행 | AI 전용 상태에 의미 결합 | To Do / In Progress / Review / Done으로 매핑 |
| 결정 필요·실패 | 전용 상태에 의존 가능 | 기존 업무 상태 유지 + Router 보류 사유 + 필요한 Jira 댓글 |
| 실행 권한 | 기존 승인·계약·lease | 그대로 유지. 라벨은 참여 조건이며 단독 실행 승인 아님 |
| 설정 경험 | 상태 전환 규칙 학습 | 기존 Jira 흐름과 Router UI의 라벨 추가·제거 사용 |

제안 기본 라벨은 `ai-enabled`다. 프로젝트별로 한 개를 설정하고 대소문자·공백 처리 규칙을 문서화한다. 역할·모델·위험도마다 필수 라벨을 추가하지 않는다. PM이 만든 하위 티켓에도 opt-in을 무조건 전파하지 않으며, 승인된 계획의 배포 정책과 준비 검사를 통과한 경우에만 Router가 부여한다.

### 실행 조건과 상태 매핑

실행 후보 = opt-in 있음 ∧ To Do에 매핑됨 ∧ 실행 승인/입력 스냅샷 유효 ∧ 요구사항·의존성 충족 ∧ 활성 실행/보류 없음. 계획 요청과 구현 요청의 준비 조건은 구별한다. 라벨 추가나 To Do 이동만으로 승인·완료를 추정하지 않는다.

| 상황 | Jira 상태 | Router 동작 |
|---|---|---|
| opt-in 없는 To Do | To Do | AI 배정하지 않음 |
| opt-in + 준비·승인 충족 | To Do → In Progress | 중복 없는 배정과 실행 시작 |
| 정상 결과 + 필수 검증 통과 | In Progress → Review | 요약·검증·PR 근거 기록 |
| 범위 이탈·사람 결정·실패 | 현재 비종료 상태 유지 | 자동 진행 보류, 이유·필요 행동 표시. 성공/Review로 위장하지 않음 |
| 검토 후 재작업 | Review → To Do | 필요한 계약 수정·새 승인 뒤 새 attempt |
| PR merge | Review → Done | 기존 merge 정책과 유효한 결과·승인 조건 확인 |
| 수동 Done 또는 외부 상태 변경 | 최신 Jira 상태 존중 | 실행·반영 권한 재평가. 자동 되돌리기 금지 |
| opt-in 제거 | 상태는 유지 | 신규 배정 차단, 실행 중 권한 철회/취소, 늦은 결과의 자동 반영 차단 |

상태명 문자열을 하드코딩하지 않는다. 프로젝트별 상태 ID와 허용 transition ID를 확인한다. Jira status category만으로 Review를 구별할 수 있다고 가정하지 않는다. 단일 Review는 계획 검토와 구현 결과 검토를 함께 담을 수 있으므로 Router의 작업 종류·결과 기록으로 구별한다. Review 이동 자체를 계획 배포 승인으로 해석하지 않는다.

## 3. M4 핵심 티켓

각 티켓은 독립 검증 가능한 결과 하나를 목표로 한다. 크기 S/M은 상대적인 분해 참고값이며 시간·파일 수·LLM 토큰 한도가 아니다. M으로 시작한 티켓이 여러 독립 결과를 포함하면 구현 전 추가 분해한다.

### M4-00 · P0 · M3 기준선 확보 [S]

- 결과: M4 이전으로 돌아갈 수 있는 검증된 원격 기준선.
- 작업: 현재 체크아웃 지침·변경 내역·M3 범위를 확인하고 프로젝트 필수 검사를 수행한다. 비밀정보·임시 산출물을 제외해 의도한 변경만 commit/push한다. 충돌하지 않는 태그명을 정해 M3 커밋에 tag 후 원격에 반영한다. 예시 이름은 `m3-baseline-2026-10-18`이며 확정 이름이 아니다.
- 인수 기준: 원격 branch·tag가 같은 기준 커밋을 가리키고 커밋 SHA, 검사 결과, 알려진 미완료, 복구 절차가 기록된다. DB/설정 백업은 Git 태그와 별도로 확보한다. 실패 시 M4 구현 착수를 보류한다.
- 의존성: 없음. 이 티켓은 계획이며 현재 push 권한 행사나 완료를 의미하지 않는다.

### M4-01 · P0 · opt-in·상태·승인 의미 확정 [S]

- 결과: 실행 가능 여부를 한 곳에서 설명할 수 있는 정책과 ADR.
- 작업: 위 조건과 상태 매핑을 기존 승인·계획 배포·merge 정책에 대조하고 차이를 명시한다. 프로젝트별 라벨과 상태 ID 설정, 누락·충돌 시 차단 정책을 정의한다.
- 인수 기준: 라벨/상태/승인의 역할이 구별되고, 계획 Review·구현 Review·재작업·라벨 제거·Done 재개방의 동작을 결정표로 검증할 수 있다. 미설정 상태에서 임의 transition을 선택하지 않는다. 기존 상태 기반 결정과의 변경을 ADR에 남긴다.
- 의존성: M4-00.

### M4-02 · P0 · 라벨 기반 후보 선정과 실행 철회 [M]

- 결과: 라벨이 AI 참여의 단일 기준으로 동작하고 기존 실행 안전장치가 유지된다.
- 작업: 후보 조회와 배정 직전 검사에 같은 정책을 적용한다. 대기 중 제거는 배정 차단, 실행 중 제거는 기존 취소·권한 철회 경로를 사용한다. commit/push/PR 등 외부 반영 직전 재검사한다.
- 인수 기준: 무라벨·승인 없음·의존성 미충족·보류·활성 실행인 티켓은 시작하지 않는다. 제거 후 재추가해도 철회된 승인이 부활하지 않는다. 이전 attempt의 늦은 결과가 새 승인을 덮어쓰지 않는다. 취소 전 이미 발생한 원격 변경은 되돌렸다고 주장하지 않고 근거와 복구 행동을 보고한다.
- 의존성: M4-01. 기존 lease·입력 해시·취소 경로를 재사용한다.

### M4-03 · P1 · Router API에서 Jira opt-in 라벨 수정 [S]

- 결과: 인증된 Router 관리 요청으로 지정 이슈의 opt-in 라벨만 추가·제거한다.
- 작업: 기존 관리 인증과 Jira 연결을 재사용한다. 허용 프로젝트·이슈·설정 라벨을 검증하고 다른 라벨을 보존한다. 지원되는 부분 수정 API 사용 여부를 확인하며, 전체 배열 쓰기가 필요하면 재조회·충돌 감지 정책을 마련한다.
- 인수 기준: 같은 요청을 반복해도 최종 라벨이 동일하다. 권한 없음·이슈 없음·Jira 제한/오류를 구별해 반환한다. 응답 불명확 시 최신 값을 조회해 확인하며 성공으로 단정하지 않는다. actor의 실제 인증 수준·대상·변경·결과를 감사 기록에 남긴다. 공유 관리 token을 Jira Assignee 본인 인증으로 표현하지 않는다.
- 의존성: M4-01, M4-02.

### M4-04 · P1 · 웹 UI의 AI 참여 토글과 현재 상태 [S]

- 결과: 사용자가 Jira 링크가 있는 이슈 화면에서 AI 참여 여부를 확인·변경한다.
- 작업: 기존 UI에 라벨 현재값, 추가/제거 버튼, 실행 가능/보류 이유를 제공한다. 라벨 제거가 실행 취소를 요청할 수 있음을 해당 조작에 짧게 안내한다.
- 인수 기준: 서버 확인 전 성공 표시하지 않는다. 중복 클릭·실패·재조회·외부 Jira 라벨 변경을 처리한다. 기존 라벨을 훼손하지 않는다. 사용자는 실행이 안 되는 이유와 다음 행동을 알 수 있다. 라벨 변경과 실행 승인 버튼의 의미가 혼동되지 않는다.
- 의존성: M4-03.

### M4-05 · P0 · 네 가지 업무 상태 전이 적용 [M]

- 결과: AI 전용 상태 없이 정상 실행→Review→Done과 예외 보류가 동작한다.
- 작업: 설정 검증과 상태 반영 경로를 같은 매핑에 연결한다. 결정·실패 보류는 업무 상태와 별도로 저장·표시한다. 기존 journal·재시도·불확실한 쓰기 복구를 유지한다.
- 인수 기준: 전이 불가 시 실행/보고 오류로 명시하고 다른 상태로 임의 이동하지 않는다. 오래된 이벤트/결과가 사람이 바꾼 상태를 되돌리지 않는다. 실패 후 To Do 유지 때문에 자동 재실행이 반복되지 않는다. Agent 성공이나 웹 확인만으로 Done이 되지 않는다. 수동 Done은 인간 행동으로 구별하고 실행을 중단한다.
- 의존성: M4-01, M4-02.

### M4-06 · P0 · 안전한 webhook 수신·재평가 [M]

- 결과: webhook이 중복 실행이나 자기 유발 루프를 만들지 않는다.
- 작업: 기존 수신 경로의 인증/출처 검증 방식을 확인하고 배포 환경에서 지원되는 방식을 명시한다. payload 크기·형식·대상 프로젝트를 제한한다. 이벤트는 재평가 신호로 취급하고 최신 Jira 이슈를 조회해 정책을 적용한다. 영속 중복 억제와 기존 polling 조정을 연결한다.
- 인수 기준: 중복·역순·지연·댓글만 변경·Router 자체 라벨/상태/댓글 이벤트에서도 이슈별 활성 실행은 하나다. 이벤트 ID 유무에 맞는 중복 키를 사용하고 승인/attempt 수준에서도 중복을 막는다. actor만으로 모든 이벤트를 버리지 않는다. 미수신은 polling이 보완하고 재시작 후에도 보호가 유지된다. 수신 영속화 실패를 성공 응답으로 숨기지 않으며 인증 실패 이벤트는 처리하지 않는다.
- 의존성: M4-02, M4-05. 신규 큐 서비스는 도입하지 않는다.

### M4-07 · P0 · 기존 상태 기반 설정과 티켓 전환 [M]

- 결과: 기존 티켓·실행·설정이 조용히 다른 의미로 바뀌지 않는다.
- 작업: 프로젝트별 `legacy` / `label` 모드(제안)를 두고 배정 경로는 한 개만 활성화한다. dry-run으로 상태별 라벨 부여·표준 상태 매핑 후보와 예외를 출력한다. 모호한 티켓은 사람이 결정한다. 실행 중 작업은 완료 대기 또는 명시적 취소 후 전환한다.
- 인수 기준: 적용 전후 이슈 키·상태·라벨·설정·활성 attempt를 기록한다. AI 상태라는 이유만으로 Review/Done/결정 대기 티켓을 새 실행 후보로 만들지 않는다. 과거 결과의 필드 누락은 ‘미확인’으로 읽는다. DB 변경은 필요할 때만 append-only migration으로 한다. 구 Worker와 wire 의미가 달라지면 명시적 버전 거절/업그레이드 순서를 제공한다.
- 의존성: M4-02, M4-05, M4-06. 최종 마이그레이션 검증은 M4-11·12의 저장/프로토콜 변경 여부가 확정된 뒤 수행한다.

### M4-08 · P1 · 가벼운 작업 크기·범위 이탈 회귀 [S]

- 결과: M3의 범위 보호가 새 라벨/상태 흐름에서도 유지된다.
- 작업: 기존 PM/Worker 호출 안에서 목적, 범위 안/밖, acceptance, 검증 방법을 재사용한다. 독립 결과 하나를 기본으로 하고 부족한 구현 요청은 보완 요청, 복수 결과는 PM 분해로 돌린다. 계획 분석에는 구현 준비 조건을 그대로 강제하지 않는다.
- 인수 기준: 단순 변경에 불필요한 하위 티켓을 만들지 않는다. 시간·파일 수만으로 크기/부채를 확정하지 않는다. 의미상 범위 이탈 또는 새 설계 결정은 중단·증거 보존·사람 결정으로 처리하고 자동 push하지 않는다. 범위 수정 후 새 승인/attempt가 필요하다. 이미 구현된 부분은 검증 결과만 기록한다.
- 의존성: M4-02, M4-05.

### M4-09 · P1 · 간결한 Jira 보고와 주의 항목 관리 [M]

- 결과: 사람은 필요한 판단과 근거를 짧은 댓글로 확인한다.
- 작업: 댓글을 ‘변화 → 영향 → 필요한 사람 행동 → 근거 링크’ 순으로 작성한다. 정상 완료는 요약·acceptance별 pass/fail/미검증·PR/head·승인 버전, 예외는 원인·선택지·권고를 남긴다. polling/heartbeat/동일 재시도는 내부 기록으로 유지한다.
- 분류: 결정 필요·최종 실패·필수 검증 누락·개별 검토가 필요한 고위험 결과는 ‘즉시 확인’, 정상 결과는 ‘일반 검토 대기’, heartbeat·자동 재시도는 ‘내부 기록’으로 구별한다. 분류는 일반 코드로 수행하고 기존 보고 저널을 재사용한다.
- 주의 항목: issue·approval·사건 종류·원인을 기준으로 동일 사건을 묶고 최초/최근 발생, 반복 횟수, 분류 근거, 미해결/해소 상태를 보존한다. 동일 미해결 사건의 반복은 댓글을 늘리지 않는다. 해소 후 재발은 새 발생으로 이전 이력에 연결하고, 새 증거·심각도 변화·사람 행동이 필요한 해소는 의미 있는 변화로 한 번만 알린다.
- 인수 기준: 결정 필요·최종 실패·검증 누락은 Jira 댓글과 기존 UI에서 이유·다음 행동을 확인할 수 있다. 같은 사건의 재전송·재시작이 중복 댓글/주의 항목을 만들지 않는다. 일시 오류가 정상화되면 미해결 표시를 해소하되, 범위 이탈·결정 대기는 필요한 사람 결정·새 승인을 확인해야 해소한다. 해소 기록만으로 실행 승인이 생기지 않는다. 상세 내부 기록은 기존 관리 조회 경로에서 확인할 수 있다. 보고용 추가 LLM 호출은 없다.
- 의존성: M4-05, M4-08, M4-11의 결과·위험 계약. 기존 M4-09의 최소 책임 게이트 조건은 M4-11로 분리해 유지한다.

### M4-10 · P0 · 마이그레이션 리허설·회귀 검증·운영 안내 [S]

- 결과: M4를 적용·중단·복구할 수 있는 검증 기록과 runbook.
- 작업: 아래 시나리오를 자동/수동으로 분류해 실행하고 설정 예시·ADR·운영 문서를 갱신한다. 필수 검사 명령은 구현 시 실제 저장소 지침에서 확인한다.
- 인수 기준: P0 미해결 없음, M4 핵심 티켓 인수 기준 충족, 미실행 실제 연동 검사는 명시한다. 자동 검사는 Fake Jira/Worker·mock을 사용한다. 테스트 Jira/GitHub에서의 수동 연동 여부를 별도 기록한다. 기준선 이후 diff·migration·롤백 제한·운영자 다음 행동을 인계한다.
- 의존성: M4-04, M4-06, M4-07, M4-08, M4-09, M4-11, M4-12. 번호는 기존 참조를 유지하며 이 티켓은 통합 검증의 마지막에 수행한다.

### M4-11 · P0 · 최소 책임 게이트와 검토 대상 고정 [M]

- 결과: 사람이 확인하는 결과가 정확한 실행·승인·변경에 연결되고, 과거 확인이 새 결과의 승인으로 재사용되지 않는다.
- 작업: 결과를 issue·job/attempt·approval ID/inputHash·계약 버전·Git base/head에 연결한다. acceptance별 pass/fail/미검증과 검증 근거를 기록한다. 검토 기록이 있는 경로는 같은 대상을 참조하고 actor·인증 수준·시각을 남긴다. 새 검토 화면은 F01에서 구현한다.
- 고위험 판정: 프로젝트 설정으로 마이그레이션·공개 API/계약·권한 정책 등 확인할 영역을 지정하고 실제 diff의 추가·삭제·rename과 대조한다. 적용 설정 버전, 일치 규칙, 변경 위치와 Agent가 보고한 의미상 위험을 근거로 보존한다. 경로 미일치만으로 저위험을 확정하지 않으며 설정/근거 부족은 ‘미확인’으로 표시한다. 별도 위험 평가 LLM 호출은 추가하지 않는다.
- 인수 기준: 검토 기록이 다른 issue/attempt/승인/head에 적용되지 않는다. 계약 또는 head가 바뀌면 이전 기록은 이력으로 남기고 최신 승인으로 표시하지 않는다. 기존 `authorize`는 실행 권한 확인으로 유지한다. Agent 성공·공유 관리 token의 확인 표시만으로 사람 승인이나 Done을 만들지 않는다.
- 인수 기준: 고위험 결과는 검증 통과 시에도 개별 검토가 필요하다. 범위 이탈·검증 실패/누락을 일반 성공으로 처리하지 않는다. 고위험 PR의 필수 리뷰는 실제 GitHub 보호 규칙과 테스트 환경의 수동 확인으로 검증하고 앱 표시만으로 merge 차단을 주장하지 않는다. 기존 유효한 PR merge 후 Done 정책과 연결한다.
- 커밋 없는 작업: head를 만들거나 추정하지 않고 ‘커밋 없음’과 결과물 위치·검증 근거를 기록한다. 커밋 기반 최신성 검증의 한계를 표시하고 자동 검토 충족·일반 묶음 검토 대상에서 제외한다. 명시적 개별 판단을 요구한다.
- 의존성: M4-01, M4-08. 저장 계약 변경은 M4-07과 함께 구 결과의 누락 필드 읽기·Worker 호환성을 검증한다.

### M4-12 · P1 · 기본 실행·사용량 증거 보존 [S]

- 결과: 이후 부채·변경 저항·비용 분석에 필요한 최소 기록을 기존 실행 경로에서 남긴다.
- 작업: 기존 provider 사용량과 job/attempt 기록을 확인해 부족한 연결만 보완한다. 원래 요구사항/부모 티켓, 호출 종류(PM/구현 등), provider·모델, 호출 식별자, 성공/실패/재개·재작업, 제공되는 입력/출력/캐시 토큰을 연결한다. 원인은 코드 구조·요구사항 변경·환경/도구·미확인을 구별하고 Agent 추정 여부를 보존한다.
- 인수 기준: 공급자가 제공하지 않는 사용량은 0이 아닌 ‘미확인’으로 남긴다. 실패·취소된 작업의 사용량도 제공되는 범위에서 보존한다. 결과 재전송·보고 재시도로 호출/사용량을 중복 집계하지 않는다. 부모 계획과 하위 작업·재시도의 원래 요구사항 연결을 유지한다. 토큰 항목의 포함 관계를 기록해 이중 합산을 막는다.
- 인수 기준: 보고·상태 갱신·사용량 기록을 위해 별도 LLM 호출을 추가하지 않는다. 기존 관찰용 평가 호출이 있다면 PM/구현과 구분하고 배정 게이트로 확대하지 않는다. 원인 불명은 그대로 남기며 재시도나 소요 시간만으로 기술 부채를 확정하지 않는다. 구 기록은 가능한 범위만 연결하고 없는 수치를 소급 생성하지 않는다.
- 범위: 기록 보존과 최소 조회/내보내기까지다. 대시보드·요금 환산·모듈별 점수·전후 효과 비교는 F05 이후로 둔다. 기본 기록이 이미 충족되면 추가 저장 체계를 만들지 않고 검증 근거를 남긴다.
- 의존성: M4-00, M4-08의 결과 계약 확인. 저장/프로토콜 변경이 필요하면 M4-07에 통합한다.

## 4. 권장 실행 순서

`M4-00 → M4-01 → M4-02 → M4-05 → M4-06 → M4-07`

API/UI는 `M4-02 → M4-03 → M4-04`, 범위/책임/보고는 `M4-05 → M4-08 → M4-11 → M4-09` 순으로 연결한다. M4-12는 M4-08의 결과 계약 확인 후 진행한다. M4-07은 M4-11·12에서 필요한 저장 계약 변경까지 포함해 마이그레이션을 마무리하고 M4-10에서 통합 검증한다. 같은 정책을 복수 구현하지 않도록 결정표와 실행 자격 판정부터 공유한다. 병렬 구현은 파일·계약 충돌이 없는 경우에만 한다.

## 5. 전환·복구 절차

1. **기준선:** M4-00을 완료하고 운영 설정·DB·관련 Jira 값의 복구 자료를 확보한다.
2. **조사/dry-run:** 구 상태 ID, 새 매핑, 대상 이슈, 활성 실행, 수동 판단 필요 목록을 출력한다. 이 단계는 Jira를 수정하지 않는다.
3. **배정 정지:** 새 작업 배정을 멈추고 활성 실행을 drain하거나 취소한다. polling/webhook의 새 실행 생성도 함께 멈춘다.
4. **호환 배포:** legacy 모드를 유지한 채 새 코드를 배포하고 DB/Worker 호환성을 확인한다. 원본 migration을 수정하지 않는다.
5. **명시적 전환:** 검토한 대상만 라벨·상태를 변경하고 재조회한다. 부분 실패는 이슈별로 기록한다. 프로젝트 하나씩 label 모드로 바꾼다. 동일 프로젝트에서 양쪽 정책을 동시에 실행하지 않는다.
6. **관찰/재개:** 새 실행은 보류한 채 후보 목록을 대조한 뒤 배정을 재개한다. webhook 자기 루프·댓글 증가·중복 attempt를 확인한다.
7. **문제 시:** 먼저 배정 정지, 활성 작업 처리, 변경 내역 대조 후 호환 모드/버전으로 복구한다. 새 DB를 구 바이너리가 읽을 수 없으면 단순 코드 되돌리기를 하지 않는다. 백업 복원 전 이후 결과·원격 변경을 보존·조정한다. Jira 변경은 기록을 근거로 선택 복구하며 Git tag만으로 Jira/DB가 복원된다고 가정하지 않는다.

기존 AI 전용 상태의 삭제와 Jira workflow 자체 정리는 M4 배포의 선행 조건이 아니다. 충분한 관찰 후 별도 작업으로 진행한다.

| T14 | 구 DB/필드 없는 결과/구 Worker | 읽기 정책·migration 재실행 안전·명시적 호환 오류 | 07 |
| T15 | 일부 Jira 이관 실패와 롤백 리허설 | 이슈별 재개/복구 가능, 원격 변경·결과 손실 없음 | 07,10 |
| T16 | head/승인/attempt 변경·다른 이슈의 검토 기록·공유 token 확인 | 검토 대상 불일치 거절, 과거 기록은 이력으로 보존, 신원 과장 없음 | 11 |
| T17 | 기존 setup/config/worker/PM/merge 경로 | 기존 사용자 기능 회귀 없음 | 10 |
| T18 | 고위험 설정과 diff의 추가·삭제·rename, 의미상 위험·근거 누락 | 규칙/위치/설정 버전 근거 보존, 미확인 구별, 개별 검토·실제 merge 보호 확인 | 11 |
| T19 | Git 커밋 없이 직접 편집한 결과 | 커밋 없음·결과 위치·검증 한계 표시, 일반 묶음/자동 검토 충족 제외 | 11 |
| T20 | 동일 장애 반복 → 해소 → 재발, 새 증거·심각도 변화 | 반복 댓글 억제, 발생 횟수·해소 이력 보존, 의미 있는 변화만 새로 노출 | 09 |

| T23 | 보고 재시도·UI 갱신·위험 규칙 검사 | 추가 LLM 호출 없음, 기존 관찰 호출과 실행 호출 구분 | 09,11,12 |

자연어 작업 크기와 의미상 이탈은 대표 사례를 사람이 함께 검토한다. 필수 프롬프트 문구나 경로 검사만으로 의미 판정 품질을 입증했다고 보고하지 않는다.

## 8. M4 완료 보고 양식

- 기준선 branch/tag/SHA와 M4 커밋, 실제 확인한 구현 범위.
- 티켓별 완료/미완료·인수 근거와 사용자에게 달라진 동작.
- 기존 결정과 달라진 ADR, label/status 설정, legacy 전환 결과.
- 자동 검사·수동 사례·실제 연동 결과와 미실행 항목.
- DB/Worker 호환성, 이관 실패·복구 결과, 남은 운영 제약.
- 범위 이탈·책임·보고 보호의 회귀 결과와 추가 LLM 호출 유무.
- 검토 대상 식별·고위험 근거·커밋 없는 결과·주의 항목 해소/재발의 검증 결과.
- 사용량 기록의 제공/누락 범위, 원래 요구사항 연결·중복 집계 검사와 아직 수행하지 않은 분석.
- 기존 M4~M7의 승계표 기준 누락 여부와 후속으로 미룬 인수 조건.
- 후속 F01~F07 중 채택한 항목. 구현하지 않은 계획을 완료로 표시하지 않는다.
